## 1. Основные решения и область работы

Нужно два основных модуля:

1. **Подготовка данных:** принять путь к каталогу сырых Olist CSV, собрать датасет, очистить и разбить на батчи.
2. **Авто-EDA:** принять один батч и эталон, автоматически и детерминированно оценить data drift, создать и исполнить notebook, затем получить HTML.

Над ними — тонкий координатор: команда `update` обрабатывает один следующий батч и сохраняет позицию потока.

Термин пользователя **«рабочий датасет»** означает итоговые **35 колонок после удаления строк с любым пропуском**, отсортированные по времени покупки.

Отчёты содержат **ровно три графика без панелей**. Панель считается отдельным графиком. Выбраны цена, товарные категории и штаты покупателей; графика пропусков нет, поскольку подготовленные батчи полные.

Эталон **динамический: все ранее успешно обработанные батчи вместе**. Раннее предложение фиксированного эталона отменено. Текущий батч сравнивается с прошлой историей до своего включения в неё.

Модельные этапы — дальнейшее развитие. Пользователь описал будущий цикл:

```text
новый батч
  → data drift + проверка качества текущих моделей / model drift
  → отчёты
  → обновление моделей
  → сохранение новой версии
  → отчёт по обновлённым моделям
```

Сейчас реализуется часть про данные и отчёты. Генерация синтетических пользовательских историй и обучение моделей в текущую поставку не входят. Поток состоит из реальных строк рабочего датасета Olist.

### Разбиение

Для `N` строк рабочего датасета:

1. Первый батч: первые `N // 2` строк.
2. Остаток: последовательные батчи по `batch_size`, по умолчанию **5 000**.
3. **Неполный последний батч отбрасывается (`drop_last=True`).** Если остаток делится на размер батча точно, сохраняются все полные батчи.
4. Позиции одного заказа разрешено разделять между батчами.

Пользователь подтвердил именно такую трактовку последнего батча в итоговом плане. Раннее предложение сохранять маленький хвост отменено.

Для имеющегося снимка по ранее сохранённым проверкам ожидаются:

- До нового удаления пропусков: 96 068 строк × 35 колонок.
- После удаления 2 046 неполных строк: **94 022 строки рабочего датасета**.
- Первый батч: **47 011 строк**.
- Последующие: **9 батчей по 5 000 строк**.
- Хвост **2 011 строк** остаётся в рабочем датасете, но не поступает в поток.
- Всего: **10 батчей**. Это ожидаемые значения для текущих источников, а не константы реализации.

Манифест должен сохранять параметры подготовки, актуальный упорядоченный список батчей, их размеры и временные диапазоны, статистику сборки/удаления неполных строк и размер отброшенного хвоста.

## 3. Модуль авто-EDA

Предложенное размещение: `src/prak/auto_eda.py`.

Публичный интерфейс:

```python
report_batch(batch_path, reference_paths, output_dir, ...)
```

- `reference_paths` — явный список CSV всех ранее обработанных батчей.
- Пустой список означает начальный шаг потока.
- Пороги дрейфа должны быть настраиваемыми, с согласованными значениями по умолчанию.
- Модуль возвращает результаты, достаточные для CLI: пути отчётов, корректность данных, результаты проверок и флаг дрейфа. Конкретный тип результата выбирается при реализации.

### Исполняемый отчёт

Порядок обязателен:

1. Создать `.ipynb` с кодом загрузки, расчётов, автотестов и построения графиков.
2. Исполнить notebook в отдельном ядре в окружении проекта.
3. Сохранить **выполненный** notebook с выводами.
4. Конвертировать его в HTML.

Пользователь специально выбрал этот путь вместо генерации HTML напрямую. Проверки должны действительно запускаться при исполнении notebook; это не статическая таблица заранее проставленных отметок.

В отчёте показать идентичность текущего батча и эталона, их размеры и периоды, три графика, метрики, пороги, результаты автотестов и итоговый статус. Исходные данные не импутируются при EDA.

### Ровно три графика

Все доли считаются **по позициям заказа**, включая географию покупателей.

1. **Распределение `price`:** две наложенные гистограммы эталона и текущего батча. Общие границы интервалов, Y — доля/процент позиций, X — цена BRL с логарифмической шкалой. Неположительная или неконечная цена — проблема качества данных. Основа исследования — P04, но только один график цены, без остальных панелей.
2. **Доли `product_category_name`:** парные горизонтальные столбцы. Top-10 фиксируется по первому батчу для всего потока. Остальные известные категории — «Прочие», отсутствующие в текущем накопленном эталоне — отдельная группа новых категорий. Порядок воспроизводим. Основа — P05.
3. **Доли `customer_state`:** парные горизонтальные столбцы по штатам, воспроизводимый порядок. Показывать доли позиций, не уникальных заказов; это отличается от исходного P06.

В начальном отчёте показываются три распределения самого первого батча, без фиктивного сравнения с собой.

### Формальное решение о дрейфе

| Признак | Мера | Дрейф по умолчанию |
| --- | --- | --- |
| `price` | KS D, максимум абсолютного разрыва эмпирических CDF | `D >= 0.10` |
| `product_category_name` | Total variation distance | `TVD >= 0.10` |
| `customer_state` | Total variation distance | `TVD >= 0.10` |

Для категорий:

```text
TVD = 0.5 * sum(abs(p_current(value) - p_reference(value)))
```

Суммировать по объединению **всех** значений в батче и эталоне, подставляя нулевую долю для отсутствующих. Группировка top-10 используется только для рисунка, не для метрики.

- Общий `drift_detected` — логическое ИЛИ трёх результатов.
- Пользователь принял фиксированные инженерные пороги; это не пороги p-value и не результат выполненной калибровки.
- Случайное семплирование для расчётов не нужно. Одинаковые входы и настройки должны давать одинаковые метрики и решения.
- Побайтовая идентичность HTML/ipynb с их служебными метаданными не требовалась.

### Автотесты данных внутри notebook

Пользователь подтвердил, что речь о проверках поступивших данных, а не о запуске тестов исходного кода проекта в отчёте:

- Точный набор 35 колонок и допустимые типы.
- Отсутствие пропусков.
- Уникальность ключа `(order_id, order_item_id)` в батче.
- Разбираемость дат и хронологический порядок строк по времени покупки.
- Конечная положительная цена.
- Отсутствие дрейфа отдельно по каждому из трёх признаков.

В таблице: имя проверки, «пройден / не пройден», фактическое значение и ожидаемое условие. Допустим статус **«не выполнено» с причиной** для инициализации или невозможного зависимого расчёта.

Важно различать:

- **Провал drift-теста:** обычный результат отчёта; не блокирует поток.
- **Провал проверки корректности:** сохранить отчёт, не продвигать поток и не добавлять батч к эталону. Зависимые расчёты при необходимости пометить как невыполненные.
- **Техническое исключение:** fail fast — немедленно завершить выполнение с ошибкой.

Ожидаемый провал проверки не должен превращаться в необработанный `assert`, который оборвёт notebook и не даст сформировать HTML.

Хронологическая проверка не требует цепочки `оплата <= перевозчик <= доставка`: в исходном Olist уже есть нарушения такой последовательности. Имеются в виду разбираемость дат и сортировка по времени покупки.

## 4. Координатор, команды и состояние

Предложенное размещение: `src/prak/cli.py`. Нужно подключить его к уже существующему console entry point `prak`.

Согласованный целевой интерфейс:

```bash
prak prepare --raw-dir dataset --output-dir data/olist-stream --batch-size 5000
prak eda --batch <csv> --reference <csv> ... --output-dir <report-dir>
prak update --data-dir data/olist-stream
```

`eda` должен поддерживать несколько явных файлов эталона и отсутствие эталона для первого отчёта. Точный синтаксис множественных аргументов оформить последовательно в CLI и документации.

Каждый `update`:

1. Читает манифест и сохранённую позицию потока.
2. Выбирает один следующий батч; для начального эталон пуст.
3. Использует все предыдущие успешно обработанные батчи как эталон.
4. Запускает авто-EDA.
5. После успешного сохранения отчётов и прохождения проверок корректности продвигает позицию. Дрейф этому не препятствует.

Первый успешный шаг создаёт начальный эталон. Затем второй батч сравнивается с первым, третий — с объединением первого и второго и т. д.

Состояние может хранить следующую позицию; состав эталона выводится из обработанного префикса манифеста. Не нужен постоянно работающий наблюдатель за каталогом.

### Сохранение и ошибки — специально упрощены пользователем

- Каталоги создавать с `mkdir(..., exist_ok=True)`.
- Одноимённые файлы перезаписывать.
- Не требовать пустой каталог и не вводить защиту от потери результатов: пользователь явно допускает потерю данных в учебном проекте.
- Повторная подготовка записывает новый рабочий датасет/батчи/манифест и **сбрасывает позицию потока**.
- Актуальный набор батчей брать из текущего манифеста, а не из всех CSV, случайно оставшихся в каталоге.
- При техническом сбое — fail fast. Не добавлять автоматические повторы, транзакционные откаты или восстановление частично записанных артефактов.

Предложенная структура результатов:

```text
data/olist-stream/
├── working_dataset.csv
├── manifest.json
├── state.json
├── batches/
│   ├── batch_000.csv
│   └── ...
└── reports/
    ├── batch_000/
    │   ├── report.ipynb
    │   └── report.html
    └── ...
```
