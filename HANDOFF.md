### 0.1. Кластеризатор: соглашения sklearn и первый бейзлайн

Общий контракт — обычный sklearn estimator: `fit(X, y=None) -> self`, атрибут `labels_` и `fit_predict(X, y=None) -> ndarray` формы `(n_samples,)`. Результат — только целочисленные метки строк, без собственного формата «раскраски» или обязательного аргумента `row_keys`.

- Наш `TemporalClustering` наследует **`ClusterMixin, BaseEstimator`** в этом порядке. `fit_predict` предоставляется `ClusterMixin`.
- Параметры задаются в `__init__`, сохраняются без изменения; проверки выполняются в `fit`. Поддерживаются `get_params`, `set_params`, `sklearn.base.clone`.
- Обученные публичные атрибуты имеют суффикс `_`; повторный `fit` заменяет обученное состояние. Для табличного входа следовать соглашениям `n_features_in_` / `feature_names_in_`.
- `X` на входе эксперимента — рабочий `DataFrame` в исходной схеме. Числовые sklearn-алгоритмы подключаются через стандартный `Pipeline` с нужной им предобработкой; оценка не извлекает внутренние шаги pipeline.
- Для первого временного бейзлайна достаточно `fit` / `labels_` / `fit_predict`. Оценка использует сохранённые метки; добавлять `predict` или правила назначения по сохранённым временным границам ради оценки не требуется.

Согласованная форма первого бейзлайна:

```python
TemporalClustering(n_clusters=20)
```

Алгоритм `fit`:

1. Сортировать по `order_purchase_timestamp`; одинаковые времена разрешать по `(order_id, order_item_id)`. Эти колонки фиксированы схемой.
2. Разделить отсортированные строки на **`n_clusters` последовательных частей (по умолчанию 20)** с разницей размеров максимум в одну строку. Остаток распределяется по первым частям, как у `numpy.array_split`.
3. Назначить частям метки `0 … n_clusters - 1` и сохранить `labels_` **в исходном порядке входных строк**. Входной DataFrame не переставлять на месте.

На первом батче ожидаются **7 групп по 2 070 строк и 13 групп по 2 069 строк**. При `n_samples < n_clusters` — `ValueError`. Алгоритм детерминирован, случайный seed ему не нужен. Связь меток с позициями заказа обеспечивается порядком исходных строк и их ключами.

При добавлении данных **именно реализация временного бейзлайна** заново делит накопленные строки на 20 частей. Границы могут сдвинуться, метки старых строк могут измениться. Координатор связывает актуальный массив меток с ключами и сохраняет полный снимок `labels.csv`.

### 0.2. Заменяемое расстояние: `fit` / `pairwise`

Согласован интерфейс по образцу sklearn: `BaseEstimator` для параметров и клонирования, `pairwise(X, Y=None)` по образцу `sklearn.metrics.DistanceMetric`, дополненный `fit(X, y=None) -> self`. У самого sklearn `DistanceMetric` метода `fit` нет — это наш согласованный интерфейс для заменяемых расстояний.

Первая реализация:

```python
class TimestampDistance(BaseEstimator):
    def fit(self, X, y=None):
        return self

    def pairwise(self, X, Y=None):
        ...
```

**Последнее прямое указание пользователя: `TimestampDistance.fit` ничего не делает.** Он не проверяет вход, не обучает масштабы и не устанавливает состояние готовности; просто возвращает `self`. Проверки данных выполняются в `pairwise`, который можно вызывать без предварительного `fit`.

- Расстояние между строками: **`abs(timestamp_i - timestamp_j)` в секундах**, результат `float64`.
- `pairwise(X)` возвращает квадратную матрицу `len(X) × len(X)`; она симметрична, неотрицательна, с нулевой диагональю.
- `pairwise(X, Y)` возвращает матрицу `len(X) × len(Y)`. Порядок строк и столбцов соответствует порядку входных наборов.
- Одинаковое время даёт нулевое расстояние даже для разных позиций заказа. Ключи нужны кластеризатору для разрешения равенств при сортировке, а не для расчёта расстояния.
- Для этого расстояния не нужны one-hot, scaler или 11 числовых признаков. Другие реализации расстояния можно подключить без изменения оценки.
- Конструктор — `TimestampDistance()`, столбец `order_purchase_timestamp` фиксирован в коде. Подготовка обучаемых расстояний относится к модельному этапу; в оценку поступает объект, уже готовый к `pairwise`.

### 0.3. Независимая оценка готовых меток и квота выборки

Согласованный интерфейс:

```python
evaluate_clustering(
    X,
    labels,
    *,
    distance,
    new_rows,
    max_evaluation_rows=1000,
    random_state=42,
)
```

- `X` — весь накопленный оцениваемый датасет, `labels` — готовые целочисленные метки в том же порядке.
- `new_rows` — булева маска формы `(len(X),)`, отмечающая строки **последнего добавленного батча**. Это принадлежность строк батчу, а не новые значения `cluster_id` и не изменения меток старых строк при переобучении.
- Координатор восстанавливает соответствие меток по ключам из `labels.csv`, проверяет его и строит маску по явно переданному `--new-batch`. Самой оценке схема Olist неизвестна.
- `max_evaluation_rows` — положительное целое, ограничивает только размер выборки оценки. Обучение и сохранение меток охватывают данные, выбранные реализацией модели, независимо от этого лимита.

**Подтверждённая пользователем квота:** при лимите 1000 выбрать **500 новых + 500 прежних строк**. Вторая половина выбирается именно из прежних строк, а не из общего остатка.

Порядок операций:

1. Проверить соответствие форм и типов `X`, `labels`, `new_rows` и параметры выборки.
2. Выбрать `min(max_evaluation_rows, len(X))` строк. Номинальная квота новых — `ceil(max_evaluation_rows / 2)`, прежних — `floor(max_evaluation_rows / 2)`. При нехватке одной части добрать из другой; если весь датасет меньше лимита, взять все строки. На первом шаге все строки новые.
3. Внутри частей выбирать случайно, **без возвращения**, независимо от значений меток, с `random_state=42`. Одни и те же выбранные позиции применить к данным, меткам и маске.
4. Получить `D = distance.pairwise(X_sample)`. Выборка выполняется **до построения матрицы расстояний**; при настройках по умолчанию матрица не больше `1000 × 1000`.
5. Рассчитать средний силуэт: `silhouette_score(D, labels_sample, metric="precomputed")`. Ту же выборку и ту же матрицу использовать для t-SNE в отчёте, см. раздел 0.4.

**Оценка не вызывает `fit`, `fit_predict` или `predict` у кластеризатора и не вызывает `fit` у расстояния.** Обязательного аргумента estimator нет; ей достаточно меток и готового расстояния. Оценка не требует `n_clusters`, центров или знания предобработки модели. Разные модели могут получать разные объекты расстояния.

Силуэт определён, когда на оцениваемой выборке `2 <= n_labels <= n_samples - 1`. В остальных случаях возвращать отсутствующее значение (`None`) с понятной причиной. Ошибки данных, некорректные расстояния и технические ошибки передавать как исключения, а не маскировать отсутствующим силуэтом. Отдельные размеры/распределения кластеров и дополнительные метрики в отчёт не входят.

Реализован frozen dataclass `EvaluationResult`: `silhouette`, `silhouette_reason`, `sample_positions`, выборочные `labels` и `new_rows`, исходная матрица `distances`; свойства `new_count` и `previous_count`. `X` принимается как непустой двумерный DataFrame или ndarray; seed — целое в `[0, 2**32 - 1]`. Отчёт получает данные для t-SNE без повторной выборки и пересчёта расстояний.

### 0.4. Сохранение меток и отчёт только на этапе оценки

seller_geolocation_lng

План предобработки — `ColumnTransformer(remainder="drop")`: числа через `SimpleImputer` → `StandardScaler`, категория через `SimpleImputer` → `OneHotEncoder(drop=None, handle_unknown="ignore")`. Эти настройки и конкретное расстояние оценки второго бейзлайна предстоит уточнить при его реализации. Внутренний мини-батч алгоритма отличается от батчей Olist. Пользователь разрешил простую стратегию обучения и обновления меток для бейзлайнов; детали MiniBatchKMeans и переход к `partial_fit` остаются задачей его реализации, а не общим требованием координатора. **Генератор историй отменён.**

```bash
uv run --frozen prak evaluate \
  --dataset data/olist-stream/batches/batch_000.csv \
  --new-batch data/olist-stream/batches/batch_000.csv \
  --model-dir models/olist-stream/clustering/temporal/batch_000 \
  --max-evaluation-rows 1000 \
  --random-state 42
```

После добавления следующего батча и обучения временного бейзлайна на накопленных данных:

```bash
uv run --frozen prak evaluate \
  --dataset data/olist-stream/reference.csv \
  --new-batch data/olist-stream/batches/batch_001.csv \
  --model-dir models/olist-stream/clustering/temporal/batch_001 \
  --max-evaluation-rows 1000 \
  --random-state 42
```

- `--dataset` — весь накопленный оцениваемый датасет; `--new-batch` — последний батч, уже включённый в него. Все три пути обязательны и задаются явно; относительные разрешаются от рабочего каталога команды.
- `--model-dir` содержит модель, расстояние и метки. Notebook и HTML сохраняются в этом же каталоге; дополнительный `--output-dir` оценке не нужен.
- `--max-evaluation-rows` по умолчанию `1000`, `--random-state` по умолчанию `42`. Старое имя `sample_size` заменено.
- Следовать текущим правилам проекта: каталоги создаются автоматически, одноимённые артефакты перезаписываются; `0` — успешное завершение (включая неопределённый силуэт с причиной), `2` — неверные аргументы, `1` — ошибка данных/исполнения/сохранения.

Реализован `train_clustering(batch_path, output_dir, *, strategy=train_temporal) -> TrainingPaths(model_path, distance_path, labels_path)`. Стратегия принимает DataFrame и возвращает `ModelSnapshot(model, distance, labels)`, где `labels` — таблица ключей и `cluster_id`. Через callable/closure можно передать прежнее состояние модели. `report_clustering(dataset_path, new_batch_path, model_dir, *, max_evaluation_rows=1000, random_state=42) -> ReportPaths`. ## 1. Модель работы и принятые упрощения

- Рабочий датасет — **35 колонок после удаления строк с любым пропуском и строк редких категорий товаров**, отсортированных по времени покупки. Единица наблюдения — позиция заказа. По умолчанию частота категории во всём очищенном датасете должна быть `>= 1000`.
- **Эталон — один физический CSV**, содержащий первый и все добавленные батчи. `init` создаёт или перезаписывает его; `update` добавляет явно указанный батч в существующий эталон.
- **EDA** описывает один датасет. **DEDA** (data-drift EDA) сравнивает текущий эталон с новым батчем до его добавления.
- После каждого создания или обновления эталона вызывается EDA уже сохранённого эталона. При обновлении получаются два разных отчёта: DEDA до добавления и EDA после него.
- `eda` и `deda` — самостоятельные пользовательские команды. Координатор вызывает те же Python-функции пакета.
- Входные пути задаёт пользователь. Автоматический выбор батча, продвижение позиции и сбор эталона из списка старых батчей в новый этап не входят.
- Исторические отчёты сохраняются **для человека**. Новые шаги используют текущие CSV; старые HTML/ipynb программно не читаются. Версии эталона и машинная история результатов не требуются.
- Пользователь выбрал **fail-fast** для учебного проекта с одним датасетом: строгая загрузка, немедленная ошибка при нарушении корректности, без диагностического reader и восстановления после сбоев.
- Реализованный модельный этап описан в разделе 0. README актуализирован: генератор синтетических историй отменён, первый бейзлайн — временной, обучение и оценка разделены.

### Готовые точки подключения

- `report_dataset(...)`, `report_drift(...)` и `initialize_reference(...)` возвращают `ReportPaths` из `auto_eda/notebook.py`: абсолютные `notebook_path` и `html_path`. `update_reference(...)` возвращает `UpdateReports(deda, eda)` с двумя `ReportPaths`.
- `check_dataset(frame)` возвращает DataFrame с колонками `Проверка`, `Результат`, `Фактически`, `Ожидается`; при первом нарушении выбрасывает `ValueError`. CSV предварительно читается через `read_dataset`.
- `execute_report(cells, output_dir, *, title)` принимает список ячеек `nbformat`, сохраняет исходный notebook, исполняет его с `sys.executable`, сохраняет выполненные ячейки и экспортирует HTML через шаблон `basic` со встроенными стилями и PNG. Ошибки передаются вызывающему коду; частичный notebook сохраняется в `finally`.
- Пути входов EDA/DEDA преобразуются в абсолютные до запуска ядра; его рабочий каталог — каталог отчёта.
- `initialize_reference` сначала проверяет батч, затем записывает его с `DATE_FORMAT` и сортировкой по `SORT_KEY`, после чего вызывает `report_dataset`. `update_reference` после успешного DEDA перечитывает оба CSV, объединяет, сортирует и записывает их в том же формате, затем вызывает EDA.
- `DriftThresholds(price=0.1, category=0.1, state=0.1)` — frozen dataclass с валидацией конечности и `[0,1]`. `evaluate_drift(reference, batch, *, thresholds=...)` возвращает `DriftResult.metrics` с колонками `Признак`, `Мера`, `Значение`, `Порог`, `Дрейф` и свойство `drift_detected` (ИЛИ). Отчёт отдельно показывает непройденные проверки отсутствия дрейфа; исключения не возникает.

Согласованная форма Python-интерфейсов:

```python
# prak.auto_eda
report_dataset(dataset_path, output_dir)
report_drift(
    batch_path,
    reference_path,
    output_dir,
    *,
    thresholds=DriftThresholds(),
)

# prak.update
initialize_reference(batch_path, reference_path, output_dir)
update_reference(
    batch_path,
    reference_path,
    output_dir,
    *,
    thresholds=DriftThresholds(),
)
```

Пути принимаются как `Path | str`. Для решения координатора достаточно обычного завершения функции или исключения: успешное завершение DEDA разрешает обновление. Не вводить `result.json`, извлечение статуса из выводов notebook или чтение старых отчётов ради управления шагом. Функции возвращают пути созданных отчётов для вывода CLI.

## 4. Проверки, дрейф и ошибки

### Обязательные проверки корректности

Загрузка — через строгий `read_dataset`. Ошибки схемы, типов или дат сразу завершают выполнение; пользователь отклонил отдельный диагностический путь чтения.

Для одного датасета, а в DEDA для обоих входов:

- Точный набор и порядок 35 колонок, допустимые типы и разбираемость дат.
- Непустой датасет: хотя бы одна позиция для вычисления распределений.
- Отсутствие пропусков.
- Уникальность ключа `ROW_KEY = (order_id, order_item_id)`.
- Хронологический порядок строк по времени покупки.
- Конечная положительная цена.

**В DEDA дополнительно проверять уникальность ключа в предполагаемом объединении эталона и батча. Допустимое число повторений — `0`.** Порог по ключу пользователь принял; процентный допуск не нужен. Повторный батч или частичное пересечение ключей блокирует запись эталона. Повторные покупки товара с разными ключами позиции допустимы. Дубликаты автоматически не удалять.

Хронологическая проверка не требует цепочки `оплата <= перевозчик <= доставка`: в Olist уже есть нарушения этой последовательности. Речь о разбираемости дат и порядке строк по времени покупки.

В нормальном отчёте показывать имя проверки, результат, фактическое значение и ожидаемое условие. В сообщении исключения указывать нарушенное условие и фактическое значение, например количество повторений ключа.

### Формальное решение о дрейфе — только DEDA

| Признак | Мера | Дрейф по умолчанию |
| --- | --- | --- |
| `price` | KS D, максимум абсолютного разрыва эмпирических CDF | `D >= 0.10` |
| `product_category_name` | Total variation distance | `TVD >= 0.10` |
| `customer_state` | Total variation distance | `TVD >= 0.10` |

```text
TVD = 0.5 * sum(abs(p_batch(value) - p_reference(value)))
```

Суммировать по объединению **всех** значений признака, подставляя нулевые доли для отсутствующих. Top-10 нужен только для графика. Общий `drift_detected` — логическое ИЛИ трёх результатов.

Это принятые пользователем инженерные пороги, не p-value и не результат калибровки. Семплирование не требуется: одинаковые входы и настройки дают одинаковые метрики и решения. Побайтовая идентичность HTML/ipynb со служебными метаданными не требуется.

### Fail-fast и сохранение

- **Дрейф — обычный результат отчёта:** показывается как непройденная проверка отсутствия дрейфа, но не вызывает исключения и не препятствует обновлению.
- **Нарушение корректности или техническая ошибка — немедленное исключение.** Ошибка внутри notebook передаётся вызывающему `init`/`update`; полный HTML при таком завершении не гарантируется.
- Если DEDA упал, добавление батча не выполняется. Если заключительный EDA упал после сохранения эталона, команда завершается с ошибкой уже на обновлённом файле.
- Каталоги создавать с `mkdir(..., exist_ok=True)`, одноимённые файлы перезаписывать. Пустой каталог не требуется; потеря прежних результатов в учебном проекте допустима.
- Автоматические повторы, транзакционные откаты и восстановление частично записанных артефактов не добавлять.

## 5. Реализованные исполняемые отчёты EDA/DEDA

Этот раздел относится к готовым EDA/DEDA. Реализованный модельный отчёт с силуэтом и t-SNE описан отдельно в разделе 0.4, результаты — в разделе 0.8.

Для обоих видов обязателен порядок:

1. Создать `.ipynb` с кодом загрузки, проверок, расчётов и графиков.
2. Исполнить его в отдельном ядре **текущего Python окружения проекта**.
3. Сохранить выполненный notebook с выводами.
4. Конвертировать его в HTML.

Ячейки могут вызывать функции соответствующих подмодулей `auto_eda/`. Проверки и расчёты должны реально запускаться внутри notebook, а не подставляться как заранее вычисленный статический результат. Проверки данных в отчёте отличаются от тестов исходного кода проекта.

**Каждый `report.html` самодостаточен:** встроенные графики, таблицы, входные пути/идентичность данных, размеры и периоды, результаты проверок, выводы; у DEDA также метрики, пороги и статус дрейфа. Для просмотра достаточно HTML, без соседних CSV, ipynb, изображений или машинного отчёта. Дополнительный `result.json` пользователь отклонил.

Общий формат: **входные данные → размеры и периоды → проверки → три графика → итог**. EDA содержит описательную статистику одного датасета; DEDA — сравнение двух входов. Исходные значения не импутируются.

### Ровно три графика в каждом нормальном отчёте

Панель считается отдельным графиком; составных рисунков с дополнительными панелями нет. Все доли — **по позициям заказа**, включая географию покупателей. Графика пропусков нет.

| Признак | EDA | DEDA |
| --- | --- | --- |
| `price` | Одна гистограмма | Две наложенные гистограммы с общими границами интервалов |
| `product_category_name` | Горизонтальные столбцы долей | Парные горизонтальные столбцы долей |
| `customer_state` | Горизонтальные столбцы долей | Парные горизонтальные столбцы долей |

- Цена: X — BRL с логарифмической шкалой, Y — доля/процент позиций. В DEDA каждое распределение нормируется на собственный размер.
- Категории: в EDA top-10 определяется по самому датасету; в DEDA — **по текущему эталону**, а не по первому батчу истории. Равные частоты разрешаются по алфавиту. Остальные известные категории — «Прочие»; в DEDA отсутствующие в эталоне категории батча — отдельная группа «Новые категории».
- Штаты: воспроизводимый порядок; для DEDA учитывать объединение значений обоих входов. Доли считать по позициям, а не по уникальным заказам, в отличие от старого исследовательского P06.

#### Принятые допущения визуальной проверки DEDA

- Внутри каждого сравнения общие интервалы и оси. Различия шкал и top-10 между независимыми шагами допустимы; фиксированная история графиков не требуется. Top-10 обязан меняться вместе с текущим эталоном.
- Полупрозрачные заливки смешиваются в зоне пересечения; принадлежность распределений читается по различимым контурам. Требование двух наложенных гистограмм сохранено.
- Малые доли штатов читаются по числовым меткам, редкие цены сохраняются в полном диапазоне; дополнительных панелей, логарифмической Y и аннотаций разности спецификация не требует. «Прочие» явно названы агрегатом и входят в полную TVD без агрегации.
- Идентичность входов, SHA-256, размеры и периоды находятся в HTML. Общие заголовки отдельных PNG допустимы: основным артефактом является самодостаточный отчёт.
- Подтверждены собственные знаменатели, полный диапазон, fail-fast для пропусков/неположительных цен, отсутствие пересечения ключей. Нули в долях штатов — отсутствие позиций, а не импутация. Сдвиг цены может отражать изменение состава товаров, географии и периода; позиции одного заказа зависимы, инженерные метрики не доказывают статистической значимости или причинности.

Критерии:

- Одинаковые распределения дают отсутствие дрейфа при порогах по умолчанию; заданные сдвиги и новые категории корректно меняют метрики и флаги. Проверены `>=`, общий флаг ИЛИ и воспроизводимость.
- Проверены строгая схема/типы/даты, пропуски, сортировка, некорректные цены и ключи. Повторный батч, частичное пересечение и внутренние повторы обнаруживаются по `ROW_KEY`.
- EDA и DEDA исполняются в окружении проекта; каждый нормальный notebook содержит ровно три графических вывода. HTML открывается самостоятельно; графики визуально проверены, включая одиночные и сравнительные варианты.
- `init` создаёт и перезаписывает эталон, затем сохраняет EDA. `update` требует существующий эталон, сохраняет DEDA до изменения и EDA после изменения. Содержимое эталона совпадает с ожидаемым объединением.
- Ошибка DEDA оставляет эталон прежним; дрейф допускает обновление. Проверен fail-fast, в том числе ошибка заключительного EDA после записи. Старые отчёты и `next_batch_index` не нужны для нового шага.
- Четыре команды проверены отдельными процессами: аргументы, справка, коды завершения, пути с пробелами и запуск из другого рабочего каталога.
- На локальном Olist выполнены `init` и несколько `update` с явными путями; проверены оба вида отчётов, размеры и ключи обновлённого эталона.
- В `pyproject.toml`/`uv.lock` явно объявлены необходимые `nbformat`, `nbclient`, `nbconvert`, `ipykernel`; README отражает фактически реализованные команды и заменяет прежний план CLI.

Этап завершён: **метрики и пересечения ключей → сравнительные графики и DEDA → update и CLI → сквозная проверка и документация**.
