# Конвейер и контракты

## Полный цикл

Локальный `run` и контейнерные `init`/`update` связывают этапы одного батча:

1. Первый батч создаёт физический эталон `reference.csv` и EDA. Следующие батчи
   проходят DEDA относительно прежнего эталона, добавляются в него, затем строится EDA.
2. Временная кластеризация заново обучается на всём эталоне; независимая оценка
   строит силуэт и t-SNE по сохранённым меткам и расстоянию.
3. Только из нового батча генерируются новые модельные пользователи.
   Прежние истории сохраняются, каталог пополняется.
4. Один выбранный ранжировщик (Random или SVD) заново обучается на накопленном
   train, затем отдельно оценивается на validation и test.
5. Публикуются метаданные завершённого шага и продвигается состояние прогона.

Docker после этого автоматически строит сводку; локально вызывается `summary`.
Параметры фиксируются на весь прогон. Автоматического переключения на лучшую
модель, поиска гиперпараметров и инкрементального обновления SVD-факторов нет.

## EDA и эталон

Вход — CSV в [схеме 35 колонок](data.md#схема-и-все-35-признаков).
Загрузка, проверки, статистика и графики исполняются в отдельном notebook-ядре
того же Python, которым запущена команда.

Обязательные проверки: точные колонки и порядок, типы и разбираемость дат,
непустой набор, отсутствие пропусков, уникальность `(order_id, order_item_id)`,
неубывание времени покупки, конечная положительная цена. Ошибка содержит
фактическое значение и ожидаемое условие; исполнение останавливается на первой.
Цепочка «оплата ≤ перевозчик ≤ доставка» не требуется. Отчёт не импутирует
пропуски и не удаляет дубликаты — очистка принадлежит подготовке.

Каждый успешный EDA содержит ровно три графика, доли считаются по позициям заказа:

1. Цена: гистограмма с 30 интервалами, логарифмической осью BRL и полным диапазоном.
2. Категории: горизонтальные столбцы top-10 и «Прочие»; равные частоты — по алфавиту.
3. Штаты покупателей: горизонтальные столбцы долей по алфавиту.

Сохраняются `report.ipynb` с результатами ячеек, самодостаточный `report.html`
со встроенными графиками и `metrics.json` (`format_version=1`, `kind="eda"`).
JSON записывается последней ячейкой из вычисленных значений: путь и SHA-256
входа, размеры/период и результаты проверок. HTML можно читать без CSV и сети;
повторное исполнение notebook требует доступных записанных в нём абсолютных путей.

Локальный `init` проверяет батч, создаёт или **перезаписывает** отсортированный
эталон и строит его EDA в `eda/`. Неверный батч отклоняется до записи. Если
notebook падает после записи, новый эталон остаётся, доступный частичный вывод
сохраняется, полный HTML не гарантируется.

## DEDA и обновление

DEDA сравнивает эталон **до добавления** с новым батчем. Проверяются оба CSV и
предполагаемое объединение; пересечения `(order_id, order_item_id)` недопустимы,
включая повторный батч. Покупки одного товара с разными ключами позиции допустимы.

| Признак | Мера | Дрейф по умолчанию |
| --- | --- | --- |
| `price` | KS D — максимальный разрыв эмпирических CDF | `D >= 0.10` |
| `product_category_name` | TVD — `0.5 × Σ abs(p_batch − p_reference)` | `TVD >= 0.10` |
| `customer_state` | TVD | `TVD >= 0.10` |

TVD учитывает все значения обоих входов, включая новые и исчезнувшие. Общий флаг —
ИЛИ трёх результатов. Семплирования нет; пороги — инженерные расстояния, не p-value.
Пороги конечны и лежат в `[0, 1]`; граница включена, поэтому порог 0 отмечает
дрейф даже при нулевом расстоянии. **Дрейф не блокирует обновление.**

Три сравнительных графика: цены с общими 30 интервалами и раздельной нормировкой;
парные столбцы категорий (top-10 по эталону, «Прочие», «Новые категории»);
парные столбцы по объединению штатов в алфавитном порядке. Доли — по позициям
соответствующего входа. В отчёте есть SHA-256 обоих CSV, размеры, периоды,
проверки, значения и пороги. `metrics.json` имеет `kind="deda"`, общий флаг и
записи `feature/measure/value/threshold/drift`.

Локальный `update` сначала сохраняет DEDA notebook **и HTML** в `deda/`, затем
объединяет CSV, сортирует и перезаписывает эталон, после чего строит EDA в `eda/`.
Ошибка DEDA оставляет эталон прежним; ошибка заключительного EDA происходит
после записи. Отката и автоматического повтора нет. Отдельный `deda` CSV не меняет.

### API отчётов

- `prak.auto_eda.report_dataset(dataset_path, output_dir) -> ReportPaths`.
- `prak.auto_eda.report_drift(batch_path, reference_path, output_dir, *, thresholds=DriftThresholds()) -> ReportPaths`.
- `prak.update.initialize_reference(batch_path, reference_path, output_dir) -> ReportPaths`.
- `prak.update.update_reference(batch_path, reference_path, output_dir, *, thresholds=DriftThresholds()) -> UpdateReports`.

`ReportPaths` содержит абсолютные `notebook_path`, `html_path`, `metrics_path`;
`UpdateReports` — `deda` и `eda`. `DriftThresholds` имеет поля `price`, `category`,
`state`. Файловые функции принимают `Path | str` и передают исключения вызывающему коду.

## Временная кластеризация

`TemporalClustering(n_clusters=20)` сортирует позиции по времени и ключу, делит
на последовательные группы с разницей размеров максимум в одну строку;
остаток распределяется по первым группам. Метки `0 … n_clusters−1` возвращаются
в исходном порядке. `fit`, `fit_predict`, `labels_`, `get_params`, `set_params`
и `clone` следуют sklearn-контракту. Повторный fit заменяет состояние.

`TimestampDistance.pairwise(X, Y=None)` вычисляет абсолютную разницу времени
покупки **в секундах**, `float64`: квадратную или прямоугольную матрицу. Fit —
no-op; проверки выполняются в pairwise, его можно вызывать без fit.
Это заданные временные группы, а не поиск естественных товарных сегментов.

Обучение сохраняет `model.joblib`, `distance.joblib`, `labels.csv` с колонками
`order_id,order_item_id,cluster_id`. Оценка выравнивает метки по ключам;
отсутствующие, лишние и повторные ключи — ошибка. Все ключи нового батча
должны входить в оцениваемый датасет. Порядок строк labels не важен.

1. Выбирается до `max_evaluation_rows=1000` строк без возвращения, независимо
   от меток: половина новых с округлением вверх, остальные прежние. Нехватка
   одной части добирается другой; если строк меньше лимита, берутся все.
2. Одна выборка и одна матрица расстояний используются для силуэта и t-SNE.
   С дефолтным лимитом матрица не больше `1000 × 1000`.
3. `silhouette_score(metric="precomputed")` требует
   `2 <= n_labels <= n_samples−1`, иначе результат `None` с причиной.
4. t-SNE: `metric="precomputed"`, `init="random"`, seed 42 по умолчанию,
   `perplexity=min(30, n−1)`, `learning_rate="auto"`. При менее чем трёх строках
   проекция пропускается с причиной. Цвет — кластер, точка — позиция заказа;
   силуэт рассчитан по исходным расстояниям, не по проекции.

Оценка не обучает модель/расстояние и не требует `predict`. Она добавляет
notebook, HTML и `metrics.json` (`kind="clustering"`) в каталог модели, включая
выборку, параметры, идентичность входов и причину неопределённого силуэта.
Неопределённый силуэт или пропуск проекции сами по себе не означают ошибку CLI.
Одноимённые артефакты перезаписываются; для истории нужны разные каталоги шагов.
При новом fit на накопленном эталоне границы групп и метки старых строк меняются.

### API кластеризации

- `train_temporal` из `prak.clustering.models.temporal` задаёт политику полного переобучения.
- `prak.clustering.training.train_clustering(batch_path, output_dir, *, strategy=train_temporal)`
  вызывает стратегию с DataFrame и сохраняет `ModelSnapshot(model, distance, labels)`.
  Возвращает `TrainingPaths(model_path, distance_path, labels_path)`.
- `prak.clustering.report.report_clustering(dataset_path, new_batch_path, model_dir, *, max_evaluation_rows=1000, random_state=42)`
  возвращает `ReportPaths`.
- `prak.clustering.evaluation.evaluate_clustering(X, labels, *, distance, new_rows, max_evaluation_rows=1000, random_state=42)`
  не зависит от Olist: X — непустой двумерный DataFrame/ndarray, labels — целые,
  new_rows — булева маска последнего батча, оба массива длины `len(X)`.
  `EvaluationResult` содержит силуэт/причину, позиции выборки, её метки, маску
  и расстояния; `new_count`/`previous_count` возвращают размеры частей.

## Модельные истории

Генератор создаёт новых пользователей из **одного нового батча** и готового
расстояния. Число пользователей не зависит от кластеров; модель и метки
кластеризации генератору не нужны.

1. Проверяются схема и отсутствие внутренних/межбатчевых повторов ключей,
   включая позиции, ранее не выбранные в истории.
2. RNG: `default_rng(SeedSequence([random_state, batch_index]))`. Сначала
   равномерно с возвращением выбирается весь массив якорей — строка на пользователя.
3. Для якоря вызывается `distance.pairwise(anchor, batch)` размера `1 × n_rows`.
   Расстояния должны быть числовыми, конечными, неотрицательными; fit не вызывается.
4. Вероятности: `p_j = exp(-d_j / temperature) / sum(exp(-d / temperature))`.
   Для устойчивости вычитается минимальное расстояние. Семплирование с возвращением,
   повторные позиции и товары разрешены. Квадратная матрица не строится.
5. Синтетическое время — целый `event_index` от нуля. Первые 70 событий идут
   в train, следующие 15 — validation, последние 15 — test по умолчанию.
   Исходное время Olist сохраняется отдельно и не пересортировывает события.
6. Добавляются только новые пользователи. Каталог пополняется всеми товарами
   нового батча, включая не выбранные при семплировании. Старые истории не меняются.

Каждый снимок самодостаточен и содержит всех пользователей поступивших шагов:

| Файл | Содержимое |
| --- | --- |
| `train.csv`, `validation.csv`, `test.csv` | `event_id,user_id,event_index,split,batch_index,product_id,order_id,order_item_id,order_purchase_timestamp` |
| `catalog.csv` | Уникальные `product_id` по алфавиту |
| `generator/anchors.csv` | `user_id,batch_index,source_position,order_id,order_item_id` |
| `generator/sources.csv` | Все исходные позиции: `batch_index,source_position,order_id,order_item_id,product_id,order_purchase_timestamp` |
| `generator/manifest.json` | Версия 1, split, RNG/NumPy, параметры батчей, пути/SHA-256 входов и файлов снимка |
| `generator/distances/batch_NNN.joblib` | Побайтовые копии использованных расстояний |

`user_id` имеет вид `user_000000_000000` (батч, пользователь), `event_id` —
`user_000000_000000:000000`. `source_position` — нулевой номер строки исходного
батча. Вероятности не сохраняются: их можно восстановить по источнику, якорю,
температуре и расстоянию. События читаются в порядке `(batch_index,user_id,event_index)`.

Продолжение проверяет SHA-256, схему, уникальность событий, якоря, split, ключи,
товары, даты и полноту каталога. Оригинальные предыдущие CSV и расстояния не нужны.
Выходной каталог должен быть новым и вне предыдущего снимка. Запись через
временный соседний каталог и переименование не оставляет частичный новый снимок
при обрабатываемой ошибке и не изменяет предыдущий.

### API генератора

Из `prak.generation`:

- `generate_histories(batch, *, distance, batch_index, n_users, temperature, split_sizes=(70, 15, 15), random_state=42)`
  работает в памяти и возвращает `GeneratedHistories(events, anchors)`.
- `generate_dataset(batch_path, distance_path, output_dir, *, temperature, previous_dir=None, n_users=None, split_sizes=None, random_state=42)`
  сохраняет накопленный снимок и возвращает `GenerationPaths` с абсолютными путями.
- `read_history_dataset(directory) -> HistoryDataset` проверяет полное состояние:
  `events`, `anchors`, `sources`, `catalog`, `manifest`.

## Ранжирование и оценка

`RankingData` содержит две таблицы: `interactions(user_id,product_id)` и
`catalog(product_id)`. Идентификаторы — непустые строки, обе таблицы непустые,
каталог уникален и покрывает все взаимодействия. Повторные покупки сохраняются.
`read_ranking_data(directory, *, split="train")` читает только выбранный CSV и каталог,
проверяет split, уникальность `event_id` и `(user_id,event_index)`, неотрицательный
целый индекс, затем оставляет две колонки взаимодействий.

Оба ранжировщика поддерживают sklearn fit/get_params/set_params/clone и
`predict(user_id, k)`: одномерный NumPy-массив K уникальных товаров по рангу.
Кандидаты — весь каталог, включая купленные ранее и отсутствующие в train товары.
Неизвестный пользователь и K вне `1 … размер каталога` — ошибки.

### Random и SVD

- `RandomRanker(random_state=42)` запоминает пользователей, полный отсортированный
  каталог и seed. Для пользователя RNG задаётся seed и целым из SHA-256 его UTF-8 ID.
  Выдача — префикс случайной перестановки каталога, стоимость O(размер каталога).
  Порядок входных строк, вызовов и `PYTHONHASHSEED` на выдачу не влияют.
- `SVDRanker(n_components=32, n_iter=7, random_state=42)` строит CSR `float32`
  счётчиков покупок: строки — отсортированные пользователи, столбцы — весь каталог.
  Бинаризации, центрирования и нормировки нет. `TruncatedSVD(algorithm="randomized")`
  даёт пользовательские векторы `C @ V` и товарные `V`; score — скалярное произведение.
  Плотная матрица score всех пользователей не строится и не сохраняется.
- SVD требует минимум два товара и `1 <= n_components <= min(пользователи, каталог)`,
  `n_iter >= 1`. Seed — целое в `[0, 2**32 - 1]`; булевы параметры не принимаются.
- Товары без train-покупок имеют нулевые векторы и score. Прочие score могут быть
  отрицательными. Сортировка по убыванию score, точные равенства — по `product_id`;
  стоимость полной сортировки O(каталог × log(каталог)). Разные K дают префиксы.
- Каждый fit заменяет обученное состояние. Для численной воспроизводимости SVD
  используйте `uv.lock` и одинаковые настройки потоков.

### Метрики и артефакты

Релевантность бинарная: множество уникальных товаров проверочного split, включая
отсутствующие в train. `Recall@K = hits / число релевантных товаров`.
`NDCG@K` использует скидку `1 / log2(rank + 1)` и идеальную выдачу длины
`min(K, число релевантных товаров)`. Итог — среднее по пользователям.
Validation предназначен для выбора настроек, test — для измерения после их фиксации.

Оценщик вызывает только predict; train, другой held-out split и `generator/`
не требуются. Файловая оценка проверяет SHA-256 каталога и совпадение полного
набора пользователей с обучением. В памяти допустимо подмножество известных
пользователей. Пустые проверочные данные и некорректная выдача — ошибки.

- `model.joblib` и `manifest.json` модели: версия 1, класс/параметры, SHA-256 модели,
  пути/хеши/размеры train и каталога, число/хеш пользователей, версии NumPy/sklearn.
- `metrics.json` оценки: версия 1, split, K, число пользователей/событий/кандидатов,
  `metrics.recall_at_k`, `metrics.ndcg_at_k`, пути и SHA-256 модели и входов.
- `per_user.csv`: `user_id,n_relevant,hits,recall_at_k,ndcg_at_k`, по пользователю.

Нужен новый каталог результата вне снимка историй; оценка может находиться внутри
модели. Запись выполняется во временный соседний каталог с публикацией переименованием.
Оценка не меняет данные или модель; хеш модели проверяется до загрузки.

### API ранжирования и inference

Из `prak.ranking`:

- `train_ranker(dataset_dir, output_dir, *, ranker=None)` клонирует ранжировщик
  (по умолчанию Random), обучает и возвращает `TrainingPaths(model_path, manifest_path)`.
- `evaluate_ranker(model, X, *, k=10)` принимает `RankingData` и возвращает метрики и `per_user` в памяти.
- `report_ranking(dataset_dir, model_dir, output_dir, *, split, k=10)` возвращает
  `EvaluationPaths(metrics_path, per_user_path)`.
- `recommend(model_dir, user_id, k=10)` возвращает DataFrame рекомендаций.
- `export_recommendations(model_dir, user_id, output_path, k=10)` сохраняет CSV
  `user_id,rank,product_id` и возвращает абсолютный путь. Ранг начинается с 1.

Inference читает только манифест и модель, проверяет версию/хеш до загрузки;
каталог модели задаётся явно. Выходной CSV должен быть вне него.
Сравнение нескольких моделей на готовых снимках описано в [benchmark](local-cli.md#сравнение-моделей).

## Состояние прогона

```text
<run-dir>/
├── config.json             # настройки, список и SHA-256 батчей, источник манифеста
├── state.json              # следующий индекс и метаданные завершённых шагов
├── reference.csv           # физический эталон последнего добавленного шага
├── steps/step_NNN/
│   ├── eda/                # report.ipynb, report.html, metrics.json
│   ├── deda/               # со второго шага
│   ├── clustering/         # model, distance, labels и отчёт
│   ├── histories/          # накопленный снимок и generator/
│   ├── ranking/            # model.joblib, manifest.json, validation/, test/
│   └── manifest.json       # входы, результаты, SHA-256 и длительности этапов
└── summary/                # создаётся командой summary или контейнерным циклом
```

Поток читается из манифеста подготовки, состояние отдельно для каждого прогона.
Перед следующим шагом проверяются конфигурация, манифест потока, очередной батч,
эталон и метаданные завершённых шагов, включая манифест историй. Генератор
дополнительно проверяет файлы предыдущего снимка по SHA-256.

Каталог шага создаётся для одного исполнения. Его манифест публикуется после
всех этапов, затем атомарно заменяется `state.json`. Это атомарность файла
метаданных, **не транзакция конвейера**. При ошибке прогресс не продвигается,
но частичные файлы и записанный эталон могут остаться. Повторный вызов на таком
шаге завершается ошибкой. Восстановление требует вручную вернуть эталон и каталог
шага к последнему завершённому состоянию либо создать новый прогон.

HTML относятся к своим шагам. Для повторного исполнения notebook старого шага
нужен соответствующий накопленный CSV: текущий эталон может содержать более поздние
батчи. Повтор всего эксперимента выполняется в новом каталоге.

Из `prak.pipeline`: `PipelineConfig`, `run_next_batch(run_dir, data_dir=..., config=...)`
возвращает `StepResult(step_index, output_dir, manifest_path)` или `None` при
исчерпании; `run_pipeline(..., all_batches=True)` — кортеж выполненных шагов.
`read_pipeline_config` читает настройки, `read_completed_steps` проверяет и
возвращает метаданные завершённых шагов.

## Сводка

`summary` собирает завершённые шаги в `summary/summary.html`, `summary.json`,
`summary.csv`: размеры эталона, проверки данных, метрики/флаги дрейфа, силуэт,
пользователей/каталог, Recall/NDCG для validation и test, гиперпараметры,
длительности и ссылки на отчёты. CSV — строка на шаг, JSON также хранит
происхождение входов и подробные метаданные. На первом шаге дрейф — `null`/пустая
ячейка; неопределённый силуэт сопровождается причиной.

Сводка проверяет контрольные суммы и согласованность оценок с обучением.
Она читает JSON, не исходные батчи, эталон, HTML, notebook или бинарные модели.
Незавершённый шаг игнорируется; отсутствие завершённых шагов — ошибка.
Повторный вызов обновляет три файла. HTML самодостаточен, подробные отчёты
доступны по ссылкам внутри прогона.

`prak.summary.report_summary(run_dir)` возвращает
`SummaryPaths(json_path, csv_path, html_path)`.
