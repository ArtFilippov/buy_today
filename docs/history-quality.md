# Качество синтетических историй

[Локальный CLI](local-cli.md#качество-историй) · [Формат снимка](pipeline.md#модельные-истории)

`history-quality` оценивает категориальный состав готового синтетического датасета
целиком: **train + validation + test**. Все повторные события учитываются.
Это описательный отчёт: большие концентрации и доли пользователей не блокируют
генерацию и не превращаются в pass/fail или составной score.

## Входы и публикация

```bash
uv run buy_today history-quality \
  --dataset-dir data/olist-stream/histories/model-selection/step_000 \
  --reference data/olist-stream/batches/batch_000.csv \
  --output-dir data/olist-stream/history-quality/model-selection/step_000 \
  --iid-repeats 100 --random-state 42
```

Все три пути обязательны. Отчёт `metrics.json` атомарно публикуется в **новом
каталоге вне снимка**, в том числе после разрешения symlink. Существующий каталог
не перезаписывается. Ошибка чтения, расчёта или записи не публикует частичный отчёт.
Snapshot и reference читаются без изменений.

Reference — один CSV в [рабочей схеме](data.md#схема-и-все-35-признаков), содержащий
ровно совокупность исходных батчей снимка. Для первого шага подходит исходный
`batch_000.csv`; для накопленного снимка батчи предварительно объединяются.
Финальный reference с более поздними батчами для раннего снимка не подходит.

Проверяются SHA-256 и все инварианты полного generator snapshot, включая anchors,
sources, каталог и три split. В reference обязательны уникальные ключи
`(order_id, order_item_id)` и точное совпадение их множества с `generator/sources.csv`:
отсутствующие и лишние ключи — ошибка, даже если строки не попали в события.
Товары и время покупки должны совпадать с sources. Пустые таблицы, пропуски,
пустые/пробельные категории и неразрешимые ссылки событий или anchors — ошибка.
Порядок строк reference не влияет на метрики; рабочие проверки выполняются после
сортировки по времени в памяти.

Категории событий и anchors восстанавливаются **по ключу позиции**, а не по товару.
Сам снимок не хранит категории: переданный reference является их источником истины.
Проверка не удостоверяет совпадение всех 35 значений с первоначальными CSV:
в sources доступны только ключ, товар и время покупки. Оригинальные пути из
manifest не открываются; расстояния проверяются по хешам, но не десериализуются.

## Метрики

Пусть `n[u,c]` — число событий категории `c` у пользователя `u`,
`N[u] = sum_c n[u,c]`, `p[u,c] = n[u,c] / N[u]`.
Пользовательские средние и распределения дают каждому пользователю одинаковый вес.
Все квантили используют линейную интерполяцию (`numpy.quantile(method="linear")`).

| Поля в `metrics` | Определение |
| --- | --- |
| `category_frequency_tvd` | `0.5 * sum_c abs(q_synthetic[c] - q_reference[c])` по объединению категорий; каждое synthetic event и каждая строка reference имеют единичный вес в своей выборке |
| `user_top_category_share_mean`, `_p50`, `_p90`, `_p95`, `_p99` | Среднее и квантили `top[u] = max_c p[u,c]` |
| `users_top_category_share_ge_0_80`, `_ge_0_90`, `_ge_0_95`, `_ge_0_99` | Доли пользователей с `top[u] >=` соответствующей границы |
| `user_effective_category_count_mean`, `_p10`, `_p50` | Среднее и квантили inverse Simpson: `effective[u] = 1 / sum_c p[u,c]**2` |
| `anchor_category_event_share` | Доля всех событий, категория которых равна категории anchor соответствующего пользователя |
| `user_anchor_category_share_mean`, `_p95` | Среднее и p95 пользовательской доли событий категории своего anchor |
| `users_anchor_category_share_ge_0_95`, `_ge_0_99` | Доли пользователей с anchor share не меньше границы |
| `top_category_share_lift_vs_iid` | Среднее synthetic `top` / среднее IID `top` |
| `effective_category_count_ratio_vs_iid` | Среднее synthetic `effective` / среднее IID `effective` |

Inverse Simpson равен 1 для одной категории и `k` для `k` равномерных категорий.
Он различает истории 99/1 и 50/50, как и top share, даже если глобальные частоты
этих датасетов одинаковы. Категория anchor может не быть самой частой.
Две anchor-метрики совпадают при одинаковых длинах историй; для разных длин
event share взвешивает пользователей по длине, user mean — равномерно.

В накопленном снимке TVD может отражать разные отношения числа исходных строк
к числу сгенерированных пользователей в батчах. Reference не перевзвешивается.

## IID baseline и воспроизводимость

Для каждого повтора создаётся независимая IID-когорта с теми же длинами историй.
Категории семплируются из частот **всего переданного reference**. Для каждого
пользователя рассчитываются top share и inverse Simpson, после чего усредняются
по всем пользователям и всем повторам. Итоговые lift/ratio — **отношения средних**,
а не средние индивидуальных отношений.

- `--iid-repeats` — положительное целое, по умолчанию `100`.
- `--random-state` — целое в `[0, 2**32 - 1]`, по умолчанию `42`.
- RNG локальный: `numpy.random.Generator(numpy.random.PCG64(seed))`.
- Категории и user IDs сортируются по возрастанию. Порядок выборок: сначала
  повторы, внутри — пользователи, блоками по 1024 пользователя.
- Используются мультиномиальные счётчики — точный эквивалент независимых категорий,
  поскольку порядок событий для этих метрик не нужен. Память baseline ограничена
  числом категорий × размером блока, а не числом событий × числом повторов.
- Одинаковые данные, параметры и версии библиотек дают одинаковые метрики независимо
  от порядка входных строк. Побайтовые хеши reference меняются при перестановке CSV.
  Версии NumPy и Pandas записываются; межверсионная идентичность RNG не обещается.

Одна категория допустима: effective count и оба отношения равны 1. Однособытийные
истории в API также допустимы. Пустые истории не допускаются; деления на ноль,
`NaN` и `Infinity` в корректном отчёте нет.
IID — контроль независимого семплирования, а не модель реального покупателя,
цель оптимизации или доказанный верхний предел разнообразия.

## JSON и Python API

`metrics.json` имеет `format_version: 1` и следующие поля:

| Поле | Содержимое |
| --- | --- |
| `scope`, `quantile_method` | `train+validation+test`, `linear` |
| `n_users`, `n_events`, `n_reference_rows` | Размеры полных оцениваемых выборок |
| `metrics` | Все 20 числовых метрик из таблицы выше |
| `iid` | `repeats`, `random_state`, `rng`, `sampling`, `aggregation` и два baseline-средних: `user_top_category_share_mean`, `user_effective_category_count_mean` |
| `versions` | `numpy`, `pandas` |
| `inputs.dataset` | Абсолютный `path`, `files`: относительное имя → SHA-256 для всех проверенных файлов, включая manifest и расстояния |
| `inputs.reference` | Абсолютный `path` и `sha256` CSV |

```python
from buy_today.history_quality import evaluate_history_quality, report_history_quality

metrics_path = report_history_quality(
    "data/olist-stream/histories/example/step_000",
    "data/olist-stream/batches/batch_000.csv",
    "data/olist-stream/history-quality/example/step_000",
    iid_repeats=100, random_state=42,
)

# Расчёт в памяти, например для дальнейшей интеграции в summary:
result = evaluate_history_quality(events, anchors, reference)
```

`evaluate_history_quality` принимает DataFrame: события с `user_id` и двумя
исходными ключами, один anchor с теми же полями на пользователя, reference
с двумя ключами и `product_category_name`. Возвращает `HistoryQuality` (TypedDict):
размеры выборок, `metrics`, `iid`. Поддерживает разные положительные длины историй.
Каждая переданная строка events считается событием, все пользователи должны иметь
anchor. Полный контракт снимка, точное множество sources и хеши проверяет файловый
адаптер `report_history_quality`.
