# Рекомендательная система списка покупок

Учебный проект по заданиям `320_MLOps_task_1.pdf` и `320_MLOps_task_2.pdf`. Python-конвейер обрабатывает поток табличных данных по батчам, обновляет модели, выдаёт рекомендации и сохраняет историю качества. Доступны локальный запуск и Docker.

Основа рекомендаций — схема **user–item**. Цель первой версии — получить простой работающий прототип, самостоятельно реализовать этапы конвейера и проверить их на воспроизводимых экспериментах.

**Статус:** реализованы сквозной локальный конвейер и Docker-интерфейс `init` / `update` / `inference` с автоматической выгрузкой Olist, отчётами и логами. Один прогон использует один выбранный ранжировщик — Random или SVD; временная кластеризация и TimestampDistance обслуживают модельный этап и генерацию историй. Локальный прогон SVD прошёл все девять батчей. Итоговый объём — **MVP + локальный Docker**; GitHub-часть исключена решением от 2026-09-22, подробнее — в [границе первой версии](#граница-первой-версии).

Инструкции: [Docker / Windows PowerShell](#docker-windows-powershell), [общий локальный запуск](#общий-последовательный-запуск), [inference](#получение-рекомендаций-inference), [summary](#сводка-прогона-summary), [подготовка](#подготовка-данных-и-батчей), [EDA](#eda-и-создание-эталона), [DEDA](#deda-и-обновление-эталона), [кластеризация](#временной-бейзлайн-кластеризация-и-оценка), [истории](#модельные-пользовательские-истории), [ранжирование](#ранжирование-и-независимая-оценка). Отдельные команды каждого этапа также доступны локально.

## Docker: Windows PowerShell

Нужен Docker Desktop с запущенным **Linux engine**. Сборка и проверка выполняются из Windows PowerShell; Python и notebook-ядра исполняются внутри Linux-контейнера. Python и uv на Windows устанавливать не требуется.

Из WSL Windows PowerShell доступен по пути `/mnt/c/Windows/System32/WindowsPowerShell/v1.0/powershell.exe`; Docker-команды выполняются через него с Windows `docker.exe`.

### Сборка образа

Из корня репозитория в PowerShell:

```powershell
# Если репозиторий находится в текущем WSL-дистрибутиве:
Set-Location '\\wsl.localhost\Ubuntu\home\user\prak'
docker version
docker build -t prak:local .
if ($LASTEXITCODE -ne 0) { throw 'Image build failed' }
docker run --rm --network none prak:local --help
```

`Dockerfile` использует Python 3.13 slim, uv 0.12.6 и `uv sync --frozen`. Пакет устанавливается в образ обычной, не editable-установкой. Зависимости notebook входят в runtime; служебные файлы ядра и кеши размещаются в `/tmp`.

Во время сборки отдельная стадия скачивает ZIP [официального Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce) через публичный Kaggle API. Проверяются ZIP/CRC и точный набор **девяти непустых исходных CSV**; они помещаются в `/opt/prak/olist`. Локальный `dataset/` для сборки не нужен. Версия датасета и ожидаемые контрольные суммы не закрепляются. Исследовательский `olist_prepared_dataset.csv` в комплект не входит.

Docker может повторно использовать скачанные данные из кеша. Для нового скачивания текущего Olist:

```powershell
docker buildx build --load --no-cache-filter olist-data -t prak:local .
```

После сборки все три команды работают без сети. Образ содержит код, окружение и исходные данные; состояние эксперимента и результаты принадлежат подключённому каталогу. Такой интерфейс позволяет запускать один батч отдельным контейнером и продолжать эксперимент следующим локальным вызовом.

### Три команды и рабочая папка

Выберите рабочую папку Windows. Во **всех** запусках она подключается по одному пути `/workspace`:

```powershell
$WorkDir = Join-Path $env:USERPROFILE 'prak-workspace'
New-Item -ItemType Directory -Path $WorkDir -Force | Out-Null

docker run --rm --network none --mount "type=bind,source=$WorkDir,target=/workspace" `
    prak:local init --verbose
if ($LASTEXITCODE -ne 0) { throw 'init failed; see workspace logs' }

docker run --rm --network none --mount "type=bind,source=$WorkDir,target=/workspace" `
    prak:local update --verbose
if ($LASTEXITCODE -ne 0) { throw 'update failed; see workspace logs' }

docker run --rm --network none --mount "type=bind,source=$WorkDir,target=/workspace" `
    prak:local inference --model-dir run/steps/step_001/ranking `
    --user-id user_000000_000000 --k 10 --verbose
if ($LASTEXITCODE -ne 0) { throw 'inference failed; see workspace logs' }
```

| Команда контейнера | Результат |
| --- | --- |
| `init` | Проверка аргументов и встроенных CSV → сброс прежнего эксперимента → выгрузка девяти CSV с перезаписью → подготовка всего потока → **один первый батч** с обучением/оценкой → сводка |
| `update` | Сохранённые настройки и состояние → **один следующий батч** → обновлённая сводка |
| `inference` | Загрузка явно указанной модели → рекомендации известному модельному пользователю → CSV |

Для полного потока из девяти батчей нужны один `init` и восемь `update`. Модель переобучается на накопленных историях. При исчерпании потока `update` успешно пересобирает сводку без нового обучения. `update` требует существующий прогон; `inference` может читать отдельный сохранённый каталог модели.

```text
<WorkDir>/
├── dataset/          # девять CSV из образа
├── data/             # рабочий CSV, manifest.json, state.json и batches/
├── run/              # config/state, reference.csv, steps/, summary/
├── recommendations/  # CSV результатов inference
└── logs/             # отдельный текстовый файл на каждый вызов
```

**Повторный `init` сбрасывает эксперимент:** удаляет содержимое каталогов `data/`, `run/`, `recommendations/`, перезаписывает девять исходных CSV и снова обучается на первом батче. Старые `logs/` сохраняются побайтово; прочие файлы вне перечисленных результатов сохраняются. `update` и `inference` не выгружают исходные данные заново. Сброс и весь шаг не являются транзакциями: после ошибки остаются доступные частичные результаты, автоматического восстановления нет.

В настройках прогона фиксируются абсолютные пути **внутри контейнера**. Для продолжения сохраняйте подключение к `/workspace`. HTML-отчёты можно открыть непосредственно в Windows, например `<WorkDir>\run\summary\summary.html`.

### Параметры, verbose и логи

Справка: `docker run --rm prak:local init --help` и аналогично для остальных команд. Параметры передаются после имени команды.

- `init`: `--batch-size` (5000), `--min-category-count` (1000), а также параметры [локального общего запуска](#общий-последовательный-запуск): `--model`, `--random-state`, `--temperature`, `--initial-users`, `--additional-users`, `--split-sizes`, `--k`, `--svd-n-components`, `--svd-n-iter`, `--temporal-n-clusters`, `--max-evaluation-rows`, три порога дрейфа. По умолчанию SVD с 32 компонентами, 2000 + 250 пользователей и split 70/15/15. Параметры фиксируются при `init`; `update` загружает их из прогона.
- `inference`: обязательны `--model-dir` и `--user-id`, K по умолчанию 10. Относительный путь модели считается от `/workspace`; это явный выбор шага, а не автоматический выбор последней модели. `user_id` — синтетический идентификатор из историй, например `user_000000_000000`. Неизвестный пользователь — ошибка.
- По умолчанию inference создаёт уникальный CSV в `recommendations/`. `--output example.csv` задаёт имя относительно этого каталога; абсолютный путь также должен находиться внутри `/workspace/recommendations`.
- `--verbose` есть у каждой команды: выводит начало стадии **до выполнения**, завершение, длительность и номер батча. Видны подготовка, EDA/DEDA, кластеризация, notebook, генерация историй, обучение ранжировщика, validation/test и сводка. Вывод ячеек и графики остаются в notebook/HTML.
- Без verbose в консоли остаются итог, пути и ошибки. При любом режиме в `logs/` создаётся UTF-8 лог `<время-UTC>_<id>_<команда>.log` со стадиями, длительностями и traceback. Неверные аргументы также записываются в лог; `--help` не создаёт файлов. Ошибки аргументов дают код 2, ошибки исполнения — 1.

Событие `batch_committed` означает фиксацию завершённого батча; `command_succeeded` — успешное завершение всей команды. Сводка строится **после** фиксации. Если она падает, команда возвращает ошибку и сообщает, что батч сохранён. Следующий `update` берёт следующий батч и заново собирает сводку всех завершённых шагов; на исчерпанном потоке он только пересобирает сводку.

Контейнерные `init`/`update` — полный цикл через `prak.container_cli`. Локальные одноимённые команды `uv run prak init/update`, описанные ниже, выполняют операции с эталоном и EDA/DEDA.

### Проверка контейнера из Windows

Отдельная стадия `tests` устанавливает dev-зависимости и тесты; для неё не скачивается Olist:

```powershell
docker build --target tests -t prak-tests:local .

docker run --rm --network none prak-tests:local
if ($LASTEXITCODE -ne 0) { throw 'Tests failed' }

$CheckDir = Join-Path $env:TEMP ('prak-smoke-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\docker-smoke.ps1 -Root $CheckDir
if ($LASTEXITCODE -ne 0) { throw 'Docker smoke check failed' }
```

`ExecutionPolicy Bypass` действует на процесс, запускающий скрипт; это позволяет исполнить файл и с UNC-пути WSL. Проверочный корневой каталог должен быть новым, его родитель — существующим. Скрипт создаёт искусственный набор девяти таблиц, подставляет его вместо встроенного Olist и запускает отдельные offline-контейнеры: `init` → `update` → `inference` → исчерпанный `update` → повторный `init`. Notebook, SVD и отчёты исполняются реально. Проверяются сохранность прежних моделей/историй, восстановление сводки, сброс результатов и сохранение всех прежних логов. Проверочные JSON находятся в `<CheckDir>\checks\`, результаты — в `<CheckDir>\workspace with spaces\`.

## Данные

**Источник:** [Brazilian E-Commerce Public Dataset by Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce). Он содержит около 100 тыс. реальных анонимизированных заказов за 2016–2018 годы.

Исходные данные скачаны и распакованы в `dataset/`: 9 CSV-файлов с покупателями, геолокацией, позициями заказов, платежами, отзывами, заказами, товарами, продавцами и переводами названий категорий.

Исходная единица наблюдения — **позиция заказа**, к которой присоединяются признаки товара, продавца, заказа и при необходимости покупателя.

- `customer_unique_id` — идентификатор реального пользователя Olist.
- `product_id` — идентификатор товара.
- `order_purchase_timestamp` — исходное время покупки.
- Идентификатор позиции заказа позволяет отличать повторную покупку от дубликата записи.
- Идентификаторы пользователей, заказов и товаров служат для связей и индексации, а не автоматически включаются в признаки расстояния.

В поток поступают **реальные позиции заказов Olist**, отсортированные по исходному времени покупки. Для экспериментов с рекомендациями генератор создаёт модельных пользователей и семплирует их покупки из этих позиций по готовому расстоянию. Модельный `user_id` отличается от исходного `customer_unique_id`; время разбиения историй — порядок моделируемых событий.

Требования задания к исходной таблице:

- не менее 10 000 строк;
- не менее 10 признаков, включая минимум два категориальных;
- временная переменная;
- пропущенные значения;
- формат CSV, XLS или XLSX; для прототипа используется CSV.

### Утверждённый набор столбцов

Для первой версии используем **все 35 столбцов**, утверждённых по исследовательской таблице `dataset/olist_prepared_dataset.csv`. Команда `prepare` заново собирает их из исходных CSV и сохраняет очищенный рабочий датасет в `data/olist-stream/working_dataset.csv`. Полный перечень, краткие описания и возможные применения приведены в [таблице отбора признаков](feature_selection.md).

В выбранный набор входят идентификаторы, цена и стоимость доставки, статус и все даты заказа, адресные и географические поля покупателя и продавца, категория и характеристики товара. В том числе сохраняются `order_status`, `order_approved_at`, `order_delivered_carrier_date` и `order_delivered_customer_date` — поля ретроспективной таблицы, описывающие ход и результат покупки.

Роли столбцов в конвейере и способы их преобразования уточняются при построении пространства признаков. Идентификаторы используются для связей и индексации; временной порядок рабочего датасета определяется `order_purchase_timestamp`.

## Подготовка данных и батчей

Нужны Python 3.13+ и [uv](https://docs.astral.sh/uv/). Запуск из корня репозитория:

```bash
uv sync --frozen
uv run prak prepare \
  --raw-dir dataset \
  --output-dir data/olist-stream \
  --batch-size 5000 \
  --min-category-count 1000
```

`--raw-dir` и `--output-dir` обязательны. Размер последующих батчей по умолчанию — `5000`, минимальная частота категории — `1000`; аргументы `--batch-size` и `--min-category-count` можно опустить. Относительные пути разрешаются от текущего рабочего каталога. Справка: `uv run prak --help` и `uv run prak prepare --help`.

### Вход и правила подготовки

В исходном каталоге нужны семь файлов:

```text
olist_order_items_dataset.csv
olist_orders_dataset.csv
olist_customers_dataset.csv
olist_sellers_dataset.csv
olist_geolocation_dataset.csv
olist_products_dataset.csv
product_category_name_translation.csv
```

Платежи, отзывы и ранее сохранённый `olist_prepared_dataset.csv` для команды не требуются.

1. Оставляются позиции заказов `delivered` и товары с единственным продавцом **во всей исходной истории позиций**, включая недоставленные заказы.
2. Присоединяются покупатели, продавцы, товары и география. Проверяются ключи, ссылки на справочники и соединения `many_to_one`.
3. Почтовые префиксы сохраняются как пятизначные строки. География агрегируется по префиксу: отдельные медианы координат и наиболее частая пара «город–штат»; при равенстве частот выбирается первая пара по алфавиту.
4. Категории переводятся на английский; при отсутствии перевода сохраняется оригинал.
5. Выбираются ровно 35 колонок. Строки с любым пропуском в этих колонках удаляются; пропуски в исключённых исходных полях на очистку не влияют.
6. По всему очищенному датасету считаются частоты `product_category_name`: число позиций заказа после перевода категорий и удаления пропусков. Строки категорий с частотой **меньше `min_category_count`** удаляются; категория ровно на пороге сохраняется. Порог применяется один раз до разбиения на батчи.
7. Строки сортируются по `order_purchase_timestamp`, `order_id`, `order_item_id`. Отфильтрованный рабочий датасет сохраняется целиком.
8. Первый батч содержит `N // 2` строк, где `N` — размер после обоих фильтров. Остаток разбивается на последовательные полные батчи по `batch_size`. Неполный последний батч отбрасывается из потока, но его строки остаются в рабочем датасете. Позиции одного заказа могут попасть в разные батчи.

Размер батча и минимальная частота категории должны быть положительными целыми числами; после очистки и фильтрации категорий должны остаться минимум две строки. Порог `1` сохраняет все категории очищенного датасета. Если остаток после первого батча меньше `batch_size`, поток содержит только первый батч. Ошибки входных данных и записи завершают команду с ненулевым кодом: `2` для неверных аргументов CLI, `1` для ошибок подготовки.

```text
data/olist-stream/
├── working_dataset.csv
├── manifest.json
├── state.json
└── batches/
```

CSV записываются в UTF-8 без индекса DataFrame, даты — в формате `YYYY-MM-DD HH:MM:SS`.

| `sources` | Абсолютный исходный каталог и список семи файлов с числом строк; пути файлов относительно исходного каталога |
| `schema` | Упорядоченный список 35 колонок и их типы |
| `parameters` | Размер батча, правило первого батча, `drop_last`, сортировка, правило удаления пропусков и `min_category_count` |
| `statistics.stages` | Число строк, заказов и товаров по этапам: источник, delivered, единственный продавец, сборка, очистка (`cleaned`), фильтрация категорий (`category_filtered`) |
| `statistics` | Также число исключённых недоставленных заказов и товаров с несколькими продавцами, пропуски до очистки, `rows_dropped_missing`, `rows_dropped_rare_categories`, `categories_before_filtering`, `categories_after_filtering` и размер хвоста |
| `working_dataset` | Путь, число строк, начало и конец периода покупок |
| `batches` | Упорядоченный список актуальных батчей: `id`, `path`, `rows`, `period_start`, `period_end` |

Пути к результатам в манифесте относительны к каталогу `manifest.json`. Состав потока определяется списком `batches`, а не перебором всех CSV в каталоге.

`state.json` после подготовки содержит `{"next_batch_index": 0}` — артефакт `prepare`. Повторная подготовка перезаписывает одноимённые файлы и сбрасывает эту позицию. `init` и `update` используют явно переданные пути. `run` хранит собственное состояние внутри каталога прогона; состояние подготовки не управляет его прогрессом. Старые файлы батчей, не вошедшие в новый манифест, могут оставаться в каталоге и не относятся к актуальному потоку.

## EDA и создание эталона

### Самостоятельный отчёт: `eda`

```bash
uv run prak eda \
  --dataset data/olist-stream/batches/batch_000.csv \
  --output-dir data/manual-reports/eda
```

Вход — один существующий CSV в схеме рабочего датасета (35 колонок). Оба пути обязательны; относительные пути разрешаются от текущего рабочего каталога команды.

Отчёт строится в отдельном ядре **того же Python, которым запущена команда**. Загрузка, проверки, статистика и графики реально исполняются внутри notebook. В `--output-dir` сохраняются:

- **`report.ipynb`** — код и результаты выполненных ячеек; его можно повторно исполнить в окружении проекта, пока доступны записанные в нём абсолютные входные пути.
- **`report.html`** — самодостаточный отчёт с таблицами, встроенными графиками и выводами. Для просмотра не требуются CSV, notebook, соседние изображения или подключение к Интернету.
- **`metrics.json`** — версия формата `1`, `kind="eda"`, входной путь и SHA-256, размеры/период и результаты проверок. Записывается из вычисленных значений последней ячейкой notebook; путь доступен как `ReportPaths.metrics_path`.

Порядок разделов: входной путь и SHA-256 → размеры и период покупок → проверки → описательная статистика → три графика → итог.

Обязательные проверки: точные колонки и их порядок, типы и разбираемость дат, непустой датасет, отсутствие пропусков, уникальность `(order_id, order_item_id)`, неубывание времени покупки и конечная положительная цена. В ошибке проверки приводятся фактическое значение и ожидаемое условие. Цепочка «оплата ≤ перевозчик ≤ доставка» не требуется. Исполнение прекращается при первой ошибке; пропуски не импутируются, дубликаты не удаляются.

В каждом успешном отчёте **ровно три графика**, все доли — по позициям заказа:

1. Цена: гистограмма с 30 интервалами, логарифмической осью BRL и долей позиций в каждом интервале; весь диапазон без обрезки хвостов.
2. Категории товаров: горизонтальные столбцы top-10 по этому датасету и группы «Прочие»; равные частоты разрешаются по алфавиту.
3. Штаты покупателей: горизонтальные столбцы долей в алфавитном порядке, без дедупликации заказов или покупателей.

EDA описывает один датасет и не принимает решения о дрейфе.

### Создание или перезапись эталона: `init`

```bash
uv run prak init \
  --batch data/olist-stream/batches/batch_000.csv \
  --reference data/olist-stream/reference.csv \
  --output-dir data/olist-stream/reports/step_000
```

Все три пути обязательны. Команда:

1. Строго загружает батч и выполняет обязательные проверки.
2. Создаёт или **перезаписывает** `--reference`, сохраняя схему, CSV-форматы и сортировку по времени покупки и ключу позиции.
3. Вызывает тот же EDA для уже сохранённого эталона; отчёт размещается в `<output-dir>/eda/report.ipynb` и `<output-dir>/eda/report.html`.

Эталон — один физический CSV. Повторный `init` полностью заменяет его выбранным батчем. `manifest.json`, `state.json` и прежние отчёты не нужны. Каталоги создаются автоматически; одноимённые отчёты перезаписываются. Для истории задавайте отдельный `--output-dir` на каждый шаг.

Ошибка проверки батча возникает до записи эталона. Если EDA упал после записи, новый эталон остаётся на диске; отката нет. При ошибке notebook сохраняется доступный частичный вывод, полный HTML не гарантируется.

Коды завершения: `0` — успех, `2` — неверные аргументы CLI, `1` — ошибка данных, исполнения notebook или записи. У `eda` и `init` нет параметров дрейфа. Справка: `uv run prak eda --help`, `uv run prak init --help`.

## DEDA и обновление эталона

### Самостоятельное сравнение: `deda`

```bash
uv run prak deda \
  --reference data/olist-stream/reference.csv \
  --batch data/olist-stream/batches/batch_003.csv \
  --output-dir data/manual-reports/deda
```

Принимает один существующий эталон и один батч, сохраняет `report.ipynb`, самодостаточный `report.html` и `metrics.json` непосредственно в `--output-dir`. JSON содержит `format_version=1`, `kind="deda"`, идентичность обоих входов, пороги, флаг дрейфа и записи `feature/measure/value/threshold/drift`. CSV остаются прежними. Все три пути обязательны и могут быть относительными.

В отдельном ядре Python исполняются загрузка обоих CSV, обязательные проверки каждого входа, проверка предполагаемого объединения, метрики и графики. В отчёт входят пути и SHA-256 обоих входов, размеры и периоды, таблицы проверок, метрики с порогами и общий `drift_detected`, три сравнительных графика и итог.

**Повторения ключа `(order_id, order_item_id)` в объединении недопустимы.** Повторный батч, частичное пересечение и внутренние дубликаты вызывают ошибку. Повторные покупки одного товара с различными ключами позиции допустимы.

| Признак | Мера | Дрейф по умолчанию |
| --- | --- | --- |
| `price` | KS D — максимальный разрыв эмпирических CDF | `D >= 0.10` |
| `product_category_name` | TVD — `0.5 × Σ abs(p_batch − p_reference)` | `TVD >= 0.10` |
| `customer_state` | TVD | `TVD >= 0.10` |

TVD учитывает **все** значения обоих входов, включая новые и исчезнувшие; отсутствующим значениям соответствует нулевая доля. Общий флаг — логическое ИЛИ трёх результатов. Семплирования нет; одинаковые входы и настройки дают одинаковые метрики. Это инженерные пороги расстояний, а не p-value или калиброванные уровни значимости.

У `deda` и `update` одинаковые необязательные аргументы:

```text
--price-threshold       0.10
--category-threshold    0.10
--state-threshold       0.10
```

Разрешены только конечные числа в `[0, 1]`; сравнение включает границу. Например, порог `0` отмечает дрейф даже при нулевом расстоянии. Дрейф показывается как непройденная проверка его отсутствия, **не вызывает исключения и не блокирует обновление**.

Ровно три сравнительных графика, все доли — по позициям соответствующего входа:

1. Цена: две наложенные гистограммы с общими 30 интервалами по полному диапазону цен, логарифмической осью BRL и отдельной нормировкой каждого входа. Сплошной синий и пунктирный оранжевый контуры различают эталон и батч.
2. Категории: парные горизонтальные столбцы; top-10 определяется по **текущему эталону**, равенства — по алфавиту. Остальные известные категории — «Прочие», отсутствующие в эталоне — «Новые категории»; группы показываются при наличии.
3. Штаты: парные столбцы по объединению штатов обоих входов, алфавитный порядок.

## Временной бейзлайн: кластеризация и оценка

Первый бейзлайн — **20 последовательных равных по размеру временных групп**. Обучение и оценка разделены: `cluster` сохраняет модель, расстояние и метки, `evaluate` читает эти артефакты и создаёт отчёт. Отложенный план другой модели описан в разделе [MiniBatchKMeans](#minibatchkmeans-отложенный-план).

### Обучение: `cluster`

Первый эксперимент использует `batch_000.csv` напрямую, без предварительного создания эталона:

```bash
uv run --frozen prak cluster \
  --batch data/olist-stream/batches/batch_000.csv \
  --output-dir models/olist-stream/clustering/temporal/batch_000 \
  --model temporal \
  --distance timestamp \
  --temporal-n-clusters 20
```

`--batch` и конечный `--output-dir` обязательны. Сейчас доступны только `--model temporal` и `--distance timestamp`; они используются по умолчанию. Необязательный `--temporal-n-clusters` переопределяет параметр только временной модели: положительное целое, не больше числа входных строк. При его отсутствии CLI не передаёт число кластеров; значение `20` принадлежит реализации `train_temporal` / `TemporalClustering`. Прежний общий флаг `--n-clusters` заменён этим модельным флагом.

- `TemporalClustering(n_clusters=20)` сортирует позиции по `order_purchase_timestamp`, при равенстве — по `(order_id, order_item_id)`, и делит их на последовательные части с разницей размеров максимум в одну строку. Остаток распределяется по первым частям. Метки `0 … n_clusters - 1` возвращаются в исходном порядке строк; входной DataFrame не переставляется. Алгоритм детерминирован.
- Кластеризатор следует sklearn-контракту: `fit(X, y=None) -> self`, `labels_`, `fit_predict`, `get_params`, `set_params`, `clone`. Повторный `fit` заменяет обученное состояние.
- `TimestampDistance()` вычисляет абсолютную разницу времени покупки **в секундах**, `float64`. `pairwise(X)` возвращает квадратную матрицу, `pairwise(X, Y)` — прямоугольную. Его `fit(X, y=None)` — no-op, возвращающий `self`; проверки выполняются в `pairwise`, который можно вызывать без `fit`.

Вход — рабочий DataFrame в схеме Olist. Время и ключи фиксированы в `schema.py`; отдельного параметра выбора столбца времени нет.

### Оценка готовых меток: `evaluate`

```bash
uv run --frozen prak evaluate \
  --dataset data/olist-stream/batches/batch_000.csv \
  --new-batch data/olist-stream/batches/batch_000.csv \
  --model-dir models/olist-stream/clustering/temporal/batch_000 \
  --max-evaluation-rows 1000 \
  --random-state 42
```

Все три пути обязательны: `--dataset` — весь накопленный оцениваемый датасет, `--new-batch` — последний уже включённый в него батч, `--model-dir` — каталог артефактов обучения. На первом шаге датасет совпадает с батчем, все строки новые. Параметры оценки по умолчанию — `max_evaluation_rows=1000`, `random_state=42`; лимит должен быть положительным целым, seed — целым в `[0, 2**32 - 1]`.

Оценка восстанавливает метки по ключам `(order_id, order_item_id)` из `labels.csv`. Отсутствующие, лишние или повторные ключи — ошибка; все ключи последнего батча должны входить в датасет и иметь метки. Порядок строк файла меток не важен.

1. По умолчанию выбирается не более 1000 строк **без возвращения**, независимо от меток: **500 новых + 500 прежних**. При другом лимите новым отводится половина с округлением вверх, прежним — вниз; при нехватке одной части добирается другая. Если датасет не больше лимита, берутся все строки. На первом шаге вся выборка состоит из новых строк.
2. Расстояния вычисляются после выборки: по умолчанию матрица не больше `1000 × 1000`. **Одна выборка и одна исходная матрица** используются для силуэта и t-SNE.
3. Силуэт считается через `silhouette_score(..., metric="precomputed")`. При нарушении условия `2 <= n_labels <= n_samples - 1` результат — `None` с причиной. Ошибки данных, расстояний и исполнения передаются как исключения.
4. t-SNE строит двумерную проекцию с `metric="precomputed"`, `init="random"`, `random_state` из параметров оценки, `perplexity=min(30, n - 1)`, `learning_rate="auto"`, где `n` — размер выборки. При менее чем трёх строках проекция пропускается с причиной. Точка — позиция заказа, цвет — метка кластера, оси — `t-SNE 1` и `t-SNE 2`. Силуэт рассчитан по исходным расстояниям.

Оценка использует готовые метки и расстояние: она не вызывает обучение кластеризатора или расстояния и не требует `predict`. Модель загружается в отчёте для показа параметров. Разные модели могут оцениваться со своими расстояниями.

### Python API

```python
from functools import partial

from prak.clustering.distances import TimestampDistance
from prak.clustering.models.temporal import train_temporal
from prak.clustering.report import report_clustering
from prak.clustering.training import train_clustering

batch = "data/olist-stream/batches/batch_000.csv"
model_dir = "models/olist-stream/clustering/temporal/batch_000"
paths = train_clustering(
    batch, model_dir,
    strategy=partial(train_temporal, n_clusters=20, distance=TimestampDistance()),
)
report = report_clustering(
    batch, batch, model_dir, max_evaluation_rows=1000, random_state=42,
)
print(paths.model_path, paths.distance_path, paths.labels_path)
print(report.notebook_path, report.html_path)
```

- `train_clustering(batch_path, output_dir, *, strategy=train_temporal) -> TrainingPaths` читает и проверяет вход, вызывает стратегию и сохраняет три артефакта. Стратегия принимает DataFrame и возвращает `ModelSnapshot(model, distance, labels)`, где `labels` — таблица ключей и `cluster_id`. `TrainingPaths` содержит абсолютные `model_path`, `distance_path`, `labels_path`.
- `report_clustering(dataset_path, new_batch_path, model_dir, *, max_evaluation_rows=1000, random_state=42) -> ReportPaths` возвращает абсолютные `notebook_path` и `html_path`. Файловые функции принимают `Path | str`.
- Независимая `prak.clustering.evaluation.evaluate_clustering(X, labels, *, distance, new_rows, max_evaluation_rows=1000, random_state=42) -> EvaluationResult` принимает непустой двумерный DataFrame или ndarray, целочисленные метки и булеву маску последнего батча в том же порядке, оба массива формы `(len(X),)`. Она не зависит от схемы Olist; `new_rows` означает принадлежность батчу, а не изменение номера кластера.
- `EvaluationResult` содержит `silhouette`, `silhouette_reason`, `sample_positions` (позиции в исходном `X`), `labels` и `new_rows` выбранных строк, `distances` — их матрицу расстояний. Свойства `new_count` и `previous_count` возвращают фактические размеры частей выборки. Готовый объект расстояния должен предоставлять `pairwise(X, Y=None)`.

### Генерация первого и следующего шага

После сохранения `TimestampDistance` командой `cluster`:

```bash
uv run --frozen prak generate \
  --batch data/olist-stream/batches/batch_000.csv \
  --distance models/olist-stream/clustering/temporal/batch_000/distance.joblib \

```

`TimestampDistance` не имеет обученного состояния, поэтому в обоих шагах используется один готовый артефакт. Можно передать другое готовое расстояние для нового шага; прежние истории сохраняются без пересемплирования.

| Аргумент | Правило |
| --- | --- |
| `--batch`, `--distance`, `--output-dir` | Обязательные пути: новый CSV Olist, готовый joblib с `pairwise(X, Y)`, новый каталог результата |
| `--previous-dir` | Предыдущий накопленный снимок; при отсутствии создаётся первый шаг |
| `--temperature` | Обязательное конечное положительное число **в единицах расстояния**; для временного эксперимента — 86 400 секунд |
| `--n-users` | Число новых пользователей: по умолчанию 2 000 на первом шаге, 250 на последующих |
| `--split-sizes TRAIN VALIDATION TEST` | Положительные целые длины частей: изначально `70 15 15`; затем наследуются. Их изменение при продолжении — ошибка |
| `--random-state` | Seed в `[0, 2**32 - 1]`, по умолчанию 42 |

Индекс батча определяется снимками: первый — `0`, каждый следующий — предыдущий плюс один. Имена входных файлов на него не влияют. Температура не имеет универсального значения по умолчанию: для другого расстояния требуется собственная калибровка.

### Правила моделирования

1. Проверяется полная рабочая схема Olist; внутренние и межбатчевые повторы `(order_id, order_item_id)` отклоняются, включая ранее не выбранные в истории позиции.
2. RNG — `np.random.default_rng(np.random.SeedSequence([random_state, batch_index]))`. Сначала равномерно с возвращением выбирается весь массив якорей — одна строка нового батча на пользователя.
3. Для каждого якоря вызывается `distance.pairwise(anchor, batch)`, матрица `1 × n_rows`. Расстояния должны быть числовыми, конечными и неотрицательными. Обучение расстояния не вызывается.
4. Вероятности строк: `p_j = exp(-d_j / temperature) / sum(exp(-d / temperature))`. Для численной устойчивости перед экспонентой вычитается минимальное расстояние. История семплируется с возвращением; повторные позиции и товары разрешены.
5. **`event_index` — синтетическое время**, целый номер события пользователя с нуля. Первые 70 событий относятся к train, следующие 15 — к validation, последние 15 — к test. Исходная дата Olist хранится отдельно; по ней события не пересортировываются.
6. К прежним событиям добавляются только новые пользователи и истории. Каталог расширяется всеми уникальными товарами нового исходного батча, в том числе не выбранными при семплировании.

Полная квадратная матрица расстояний не строится. Метки кластеров, модель кластеризации и накопленный эталон генератору не нужны. Изменение расстояния влияет только на новые истории.

Распределения вероятностей не сохраняются: они восстанавливаются из источника, якоря, температуры и сохранённого расстояния. Якоря и параметры генерации находятся в `generator/`; ранжировщику предназначены train-взаимодействия и каталог.

**Каталог результата должен быть новым**, вне предыдущего снимка. Запись сначала выполняется во временный соседний каталог, затем готовый снимок публикуется переименованием. Ошибка генерации или записи не меняет предыдущий снимок и не оставляет частичный новый. Для повторного эксперимента указывайте другой `--output-dir`.

При продолжении проверяются контрольные суммы, схема, уникальность событий, связь пользователей с якорями, временные split, исходные ключи, товары, даты и полнота каталога. Оригинальные файлы предыдущих батчей и расстояний не требуются. Коды CLI: `0` — успех, `2` — неверные аргументы, `1` — ошибка данных, расстояния или записи.

## Ранжирование и независимая оценка

```bash
for step in 000 001; do
  uv run --frozen prak rank \
    --dataset-dir "data/olist-stream/histories/step_${step}" \
    --model random --random-state 42 \
    --output-dir "models/olist-stream/ranking/random/step_${step}"

  uv run --frozen prak evaluate-ranking \
    --dataset-dir "data/olist-stream/histories/step_${step}" \
    --model-dir "models/olist-stream/ranking/random/step_${step}" \
    --split validation --k 10 \
    --output-dir "models/olist-stream/ranking/random/step_${step}/validation"

  uv run --frozen prak evaluate-ranking \
    --dataset-dir "data/olist-stream/histories/step_${step}" \
    --model-dir "models/olist-stream/ranking/random/step_${step}" \
    --split test --k 10 \
    --output-dir "models/olist-stream/ranking/random/step_${step}/test"
done
```

Обучение каждого шага использует весь его накопленный train. `--model` по умолчанию `random`, seed — `42`, K — `10`; `--split` обязателен. Validation предназначен для выбора настроек, test — для итогового измерения с зафиксированными настройками.

### Контракт данных, выдачи и метрик

- `RankingData(interactions, catalog)` содержит ровно две таблицы: `interactions` с колонками `user_id`, `product_id` и `catalog` с одной колонкой `product_id`. Идентификаторы — непустые строки; обе таблицы непустые; каталог уникален и покрывает все взаимодействия. Повторные покупки остаются отдельными строками.
- `read_ranking_data(directory, *, split="train")` открывает только выбранный CSV и `catalog.csv`. Проверяет теги split, уникальность `event_id` и `(user_id, event_index)`, неотрицательный целый `event_index`, затем оставляет только две колонки взаимодействий. Проверка полного происхождения событий принадлежит `read_history_dataset` генератора.
- `RandomRanker(random_state=42)` поддерживает `fit(X, y=None) -> self`, `get_params`, `set_params`, `clone`. Fit запоминает известных пользователей, лексикографически отсортированный полный каталог и seed в `user_ids_`, `catalog_`, `random_state_`.
- `predict(user_id, k)` возвращает одномерный NumPy-массив K уникальных `product_id` по порядку ранжирования. Ранее купленные и отсутствующие в train товары остаются кандидатами. Неизвестный пользователь и K вне `1 … размер каталога` — ошибки. Seed — целое в `[0, 2**32 - 1]`; булевы значения не принимаются вместо целых параметров.
- Для каждого пользователя создаётся RNG `default_rng(SeedSequence([seed, user_seed]))`, где `user_seed` — целое из SHA-256 UTF-8 `user_id` (big-endian). Выдача — префикс случайной перестановки каталога. Она одинакова при повторных вызовах и после загрузки; порядок строк, вызовов и `PYTHONHASHSEED` не влияют. При увеличении K прежняя выдача остаётся префиксом. Один вызов строит перестановку за O(размер каталога).
- Релевантность бинарная: множество уникальных проверочных товаров пользователя, включая отсутствующие в train. `Recall@K = hits / число релевантных товаров`; `NDCG@K` использует скидку `1 / log2(rank + 1)` и идеальную выдачу длины `min(K, число релевантных товаров)`. Итог — среднее по пользователям. Пустая проверочная таблица или некорректная выдача приводят к ошибке.
- Оценка вызывает только `predict(user_id, k)`. Из снимка читает выбранный held-out split и каталог; train, второй held-out split и `generator/` не требуются. Файловая оценка требует совпадения SHA-256 каталога и полного набора пользователей с обучением. В памяти можно оценить выбранное подмножество известных пользователей.

### SVD на счётчиках покупок

- `SVDRanker(n_components=32, n_iter=7, random_state=42)` следует тому же sklearn-контракту: `fit(X, y=None) -> self`, `get_params`, `set_params`, `clone`; повторный fit полностью заменяет обученное состояние.
- Строки матрицы — известные train-пользователи, столбцы — **весь каталог**, оба списка упорядочены лексикографически. CSR-матрица `float32` содержит число покупок каждой пары; бинаризации, центрирования и нормировки нет. Перестановка входных строк не меняет матрицу и seeded fit.
- `TruncatedSVD` с алгоритмом `randomized` получает эту матрицу. Пользовательские векторы — `C @ V`, товарные — `V`; score равен их скалярному произведению. Сохраняются `user_ids_`, `catalog_`, `user_factors_` и `item_factors_`; плотная матрица всех пользовательских score не строится и не сохраняется.
- Каталог должен содержать минимум два товара — ограничение `TruncatedSVD`. Допустимо `1 <= n_components <= min(число train-пользователей, размер каталога)`; один пользователь допустим с одной компонентой. `n_iter >= 1`, seed — в общей границе `[0, 2**32 - 1]`. Число компонент проверяется по размерности матрицы, а не по её фактическому рангу.
- Товары без train-покупок имеют строго нулевые векторы и score. Остальные score могут быть отрицательными; они не обрезаются. Сортировка — по убыванию score, при **точном равенстве** — по `product_id`. Разные K дают префиксы одной выдачи, включая границу группы равных score. Полная сортировка занимает `O(размер каталога × log(размер каталога))` после расчёта score одного пользователя.
- На каждом накопленном шаге выполняется новый fit только на train; предыдущие факторы не обновляются инкрементально. Для воспроизводимости численного эксперимента используйте `uv.lock` и одинаковые настройки потоков.

## Общий последовательный запуск

`run` связывает готовые этапы и обрабатывает **один следующий батч**. При создании прогона каталог `--run-dir` должен быть новым, а `--data-dir` должен содержать результаты `prepare`.

```bash
# Первый батч; один выбранный ранжировщик
uv run --frozen prak run \
  --data-dir data/olist-stream \
  --run-dir models/olist-stream/runs/svd \
  --model svd

# Следующий батч: входы и параметры загружаются из прогона
uv run --frozen prak run --run-dir models/olist-stream/runs/svd

# Все оставшиеся батчи в порядке манифеста
uv run --frozen prak run --run-dir models/olist-stream/runs/svd --all
```

В текущем локальном каталоге `runs/svd` уже завершены девять шагов. Для повторного эксперимента задайте новый каталог, например `runs/svd-repeat`. Для Random создайте отдельный прогон с `--model random`. Один прогон обучает и оценивает только выбранный ранжировщик.

Первый шаг: **эталон и EDA → временная кластеризация → оценка кластеризации → генерация историй → ранжировщик → validation → test**. На следующих шагах сначала выполняется DEDA относительно прежнего эталона, затем батч добавляется в эталон и строится EDA. Временная кластеризация переобучается на всём эталоне; новые истории семплируются только из нового батча, а прежние сохраняются. Ранжировщик каждый раз обучается заново на накопленном train.

### Параметры и состояние

Параметры фиксируются в `config.json` при создании прогона:

| Параметр CLI | По умолчанию |
| --- | --- |
| `--model` | `svd` |
| `--random-state` | `42` |
| `--temperature` | `86400` секунд для TimestampDistance |
| `--initial-users` / `--additional-users` | `2000` / `250` |

При продолжении явно переданные параметры должны совпадать с сохранёнными; остальные наследуются. K и размерность SVD проверяются относительно фактического каталога/числа пользователей без автоматического уменьшения. Обучение ранжировщика и обе оценки выполняются с одним потоком BLAS/OpenMP; отдельное ядро оценки кластеризации также запускается с лимитом `1`.

```text
models/olist-stream/runs/svd/
  config.json                 # параметры, список и SHA-256 батчей, источник манифеста
  state.json                  # следующий индекс и контрольные суммы завершённых шагов
  reference.csv               # физический эталон последнего добавленного шага
  steps/
    step_000/
      eda/                    # report.ipynb, report.html, metrics.json
      clustering/             # model.joblib, distance.joblib, labels.csv и отчёт

      ranking/                # model.joblib, manifest.json
        validation/           # metrics.json, per_user.csv
        test/                 # metrics.json, per_user.csv
      manifest.json           # входы, результаты, SHA-256, длительности этапов

    ...

```

Список батчей читается из манифеста подготовки. Состояние хранится отдельно для каждого прогона. Перед следующим шагом проверяются конфигурация, манифест потока, очередной батч, текущий эталон и метаданные завершённых шагов, включая манифест историй. Сам генератор проверяет файлы предыдущего снимка по его SHA-256.

Новый каталог шага создаётся исключительно для одного исполнения. `manifest.json` шага публикуется после всех этапов; затем атомарно заменяется `state.json` с новым индексом. Это атомарность одного файла метаданных, а не транзакция всего конвейера.

**При ошибке исходное исключение пробрасывается наружу.** Прогресс не продвигается; частичные файлы и уже записанный эталон могут остаться. Повторный вызов на незавершённом шаге завершается исключением. Для восстановления нужны ручное приведение эталона и каталога шага к последнему завершённому состоянию либо новый прогон. После исчерпания потока команда успешно сообщает, что новых батчей нет.

Сохранённые HTML относятся к своему шагу. Для повторного исполнения notebook старого шага нужен соответствующий накопленный CSV: текущий `reference.csv` уже может содержать более поздние батчи. Воспроизводимый повтор всего эксперимента выполняется в новом каталоге прогона.


Команда собирает **завершённые шаги одного прогона** в `summary/summary.html`, `summary/summary.json` и `summary/summary.csv`. В Python: `prak.summary.report_summary(run_dir)` возвращает `SummaryPaths(json_path, csv_path, html_path)`.

Сводка включает размеры эталона, проверки данных, значения и флаги дрейфа, силуэт, пользователей/каталог, Recall@K и NDCG@K отдельно для validation и test, гиперпараметры, длительности этапов и ссылки на подробные отчёты. CSV содержит одну строку на шаг; JSON также сохраняет происхождение входов и подробные метаданные. На первом шаге дрейф отсутствует (`null`/пустая ячейка); неопределённый силуэт сопровождается причиной.

Сводка проверяет контрольные суммы и согласованность входов оценок с обучением. Она работает по JSON: исходные батчи, текущий эталон, HTML, notebook и бинарные модели для её построения не читаются. Частичный незавершённый шаг игнорируется; отсутствие завершённых шагов — исключение. Повторный вызов обновляет три файла сводки. HTML самодостаточен, ссылки ведут к отчётам внутри прогона.

## Граница первой версии

MVP работает локально на Python с файловыми хранилищами. Для второго задания выбран предусмотренный в `320_MLOps_task_2.pdf` вариант **локального Docker**: обучение и inference запускаются из Windows PowerShell, модели, отчёты и логи сохраняются в примонтированном каталоге. Специализированные MLOps-платформы не используются согласно заданию.

**Решение от 2026-09-22:** итоговый объём — MVP и локальный Docker. GitHub Actions, CI/CD workflow, CRON-запуски и публикация образов/артефактов через GitHub исключены из плана.

Полный цикл доступен через `run`, рекомендации — через `inference`, история качества — через `summary`. Docker предоставляет команды `init` / `update` / `inference`. Прогон с одним SVD прошёл весь подготовленный поток. По решению пользователя этап MiniBatchKMeans пропущен; текущие модели — временная кластеризация и один выбранный ранжировщик.
