# Рекомендательная система списка покупок

Учебный проект по заданию `320_MLOps_task_1.pdf`: минимальный локальный Python-конвейер, который обрабатывает поток табличных данных по батчам, обновляет модели, выдаёт рекомендации и сохраняет историю качества.

Основа рекомендаций — схема **user–item**. Цель первой версии — получить простой работающий прототип, самостоятельно реализовать этапы конвейера и проверить их на воспроизводимых экспериментах.

**Статус:** реализованы `prak prepare` (подготовка и батчи), `prak eda` / `prak deda` (исполняемые отчёты), `prak init` / `prak update` (создание и инкрементальное обновление эталона). Инструкции: [подготовка](#подготовка-данных-и-батчей), [EDA и создание эталона](#eda-и-создание-эталона), [DEDA и обновление](#deda-и-обновление-эталона). Модельные этапы остаются планом развития.

В baseline используется один профиль на пользователя без учёта дня недели. Отдельные дневные профили остаются возможным развитием первоначальной идеи.

## Данные

**Источник:** [Brazilian E-Commerce Public Dataset by Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce). Он содержит около 100 тыс. реальных анонимизированных заказов за 2016–2018 годы.

Исходные данные скачаны и распакованы в `dataset/`: 9 CSV-файлов с покупателями, геолокацией, позициями заказов, платежами, отзывами, заказами, товарами, продавцами и переводами названий категорий.

Исходная единица наблюдения — **позиция заказа**, к которой присоединяются признаки товара, продавца, заказа и при необходимости покупателя.

- `customer_unique_id` — идентификатор реального пользователя Olist.
- `product_id` — идентификатор товара.
- `order_purchase_timestamp` — исходное время покупки.
- Идентификатор позиции заказа позволяет отличать повторную покупку от дубликата записи.
- Идентификаторы пользователей, заказов и товаров служат для связей и индексации, а не автоматически включаются в признаки расстояния.

В Olist мало повторных заказов на пользователя. Поэтому для будущего обучения и оценки ранжирования запланированы **модельные датасеты с синтетическими пользовательскими историями**, построенными из строк Olist. Синтетические пользователи будут иметь собственные идентификаторы.

В текущий поток поступают **реальные позиции заказов Olist**, отсортированные по исходному времени покупки. Подготовка модельных пользовательских историй — отдельный будущий этап.

Требования задания к исходной таблице:

- не менее 10 000 строк;
- не менее 10 признаков, включая минимум два категориальных;
- временная переменная;
- пропущенные значения;
- формат CSV, XLS или XLSX; для прототипа используется CSV.

### Утверждённый набор столбцов

Для первой версии используем **все 35 столбцов**, утверждённых по исследовательской таблице `dataset/olist_prepared_dataset.csv`. Команда `prepare` заново собирает их из исходных CSV и сохраняет очищенный рабочий датасет в `data/olist-stream/working_dataset.csv`. Полный перечень, краткие описания и возможные применения приведены в [таблице отбора признаков](feature_selection.md).

В выбранный набор входят идентификаторы, цена и стоимость доставки, статус и все даты заказа, адресные и географические поля покупателя и продавца, категория и характеристики товара. В том числе сохраняются `order_status`, `order_approved_at`, `order_delivered_carrier_date` и `order_delivered_customer_date` — поля ретроспективной таблицы, описывающие ход и результат покупки.

Роли столбцов в конвейере и способы их преобразования уточняются при построении пространства признаков. Идентификаторы используются для связей и индексации; временной порядок рабочего датасета определяется `order_purchase_timestamp`.

## Подготовка данных и батчей

Нужны Python 3.13+ и [uv](https://docs.astral.sh/uv/). Запуск из корня репозитория:

```bash
uv sync --frozen
uv run prak prepare \
  --raw-dir dataset \
  --output-dir data/olist-stream \
  --batch-size 5000
```

`--raw-dir` и `--output-dir` обязательны. Размер последующих батчей по умолчанию — `5000`; аргумент `--batch-size` можно опустить. Относительные пути разрешаются от текущего рабочего каталога. Справка: `uv run prak --help` и `uv run prak prepare --help`.

### Вход и правила подготовки

В исходном каталоге нужны семь файлов:

```text
olist_order_items_dataset.csv
olist_orders_dataset.csv
olist_customers_dataset.csv
olist_sellers_dataset.csv
olist_geolocation_dataset.csv
olist_products_dataset.csv
product_category_name_translation.csv
```

Платежи, отзывы и ранее сохранённый `olist_prepared_dataset.csv` для команды не требуются.

1. Оставляются позиции заказов `delivered` и товары с единственным продавцом **во всей исходной истории позиций**, включая недоставленные заказы.
2. Присоединяются покупатели, продавцы, товары и география. Проверяются ключи, ссылки на справочники и соединения `many_to_one`.
3. Почтовые префиксы сохраняются как пятизначные строки. География агрегируется по префиксу: отдельные медианы координат и наиболее частая пара «город–штат»; при равенстве частот выбирается первая пара по алфавиту.
4. Категории переводятся на английский; при отсутствии перевода сохраняется оригинал.
5. Выбираются ровно 35 колонок. Строки с любым пропуском в этих колонках удаляются; пропуски в исключённых исходных полях на очистку не влияют.
6. Строки сортируются по `order_purchase_timestamp`, `order_id`, `order_item_id`. Рабочий датасет сохраняется целиком.
7. Первый батч содержит `N // 2` строк. Остаток разбивается на последовательные полные батчи по `batch_size`. Неполный последний батч отбрасывается из потока, но его строки остаются в рабочем датасете. Позиции одного заказа могут попасть в разные батчи.

Размер батча должен быть положительным целым числом, после очистки должны остаться минимум две строки. Если остаток после первого батча меньше `batch_size`, поток содержит только первый батч. Ошибки входных данных и записи завершают команду с ненулевым кодом: `2` для неверных аргументов CLI, `1` для ошибок подготовки.

### Результаты и метаданные

```text
data/olist-stream/
├── working_dataset.csv
├── manifest.json
├── state.json
└── batches/
    ├── batch_000.csv
    ├── batch_001.csv
    └── ...
```

CSV записываются в UTF-8 без индекса DataFrame, даты — в формате `YYYY-MM-DD HH:MM:SS`.

| Поле `manifest.json` | Содержимое |
| --- | --- |
| `format_version` | Версия формата манифеста: `1` |
| `sources` | Абсолютный исходный каталог и список семи файлов с числом строк; пути файлов относительно исходного каталога |
| `schema` | Упорядоченный список 35 колонок и их типы |
| `parameters` | Размер батча, правило первого батча, `drop_last`, сортировка и правило удаления пропусков |
| `statistics.stages` | Число строк, заказов и товаров по этапам: источник, delivered, единственный продавец, сборка, очистка |
| `statistics` | Также число исключённых недоставленных заказов и товаров с несколькими продавцами, пропуски по колонкам до очистки, число удалённых неполных строк и размер хвоста |
| `working_dataset` | Путь, число строк, начало и конец периода покупок |
| `batches` | Упорядоченный список актуальных батчей: `id`, `path`, `rows`, `period_start`, `period_end` |

Пути к результатам в манифесте относительны к каталогу `manifest.json`. Состав потока определяется списком `batches`, а не перебором всех CSV в каталоге.

`state.json` после подготовки содержит `{"next_batch_index": 0}` — артефакт `prepare`. Повторная подготовка перезаписывает одноимённые файлы и сбрасывает эту позицию. `init` и `update` используют явно переданные пути, не читают и не продвигают `state.json`. Старые файлы батчей, не вошедшие в новый манифест, могут оставаться в каталоге и не относятся к актуальному потоку.

Проверенный результат на локальном снимке Olist:

| Показатель | Значение |
| --- | ---: |
| Строк после сборки, до очистки | 96 068 |
| Удалено неполных строк | 2 046 |
| Строк в рабочем датасете | 94 022 |
| Первый батч | 47 011 |
| Последующие батчи | 9 × 5 000 |
| Отброшенный из потока хвост | 2 011 |
| Всего батчей | 10 |

Эти числа зависят от исходных данных и не зафиксированы в реализации.

### Использование из Python и тесты

```python
from pathlib import Path

from prak.preparation import prepare_data
from prak.schema import read_dataset

result = prepare_data(Path("dataset"), Path("data/olist-stream"), batch_size=5000)
working = read_dataset(result.working_dataset_path)
```

`PreparationResult` содержит пути к рабочему датасету и манифесту, число строк до и после очистки, размеры батчей и размер хвоста. `read_dataset` восстанавливает типы, даты и строковые почтовые коды; числа читаются с `float_precision="round_trip"`.

```bash
uv run pytest
```

Тесты создают небольшие исходные CSV во временных каталогах. Они проверяют фильтры, сборку и географию, очистку, воспроизводимость, границы батчей, метаданные, повторную подготовку и CLI. Локальный снимок Olist для тестов не требуется.

## EDA и создание эталона

### Самостоятельный отчёт: `eda`

```bash
uv run prak eda \
  --dataset data/olist-stream/batches/batch_000.csv \
  --output-dir data/manual-reports/eda
```

Вход — один существующий CSV в схеме рабочего датасета (35 колонок). Оба пути обязательны; относительные пути разрешаются от текущего рабочего каталога команды.

Отчёт строится в отдельном ядре **того же Python, которым запущена команда**. Загрузка, проверки, статистика и графики реально исполняются внутри notebook. В `--output-dir` сохраняются:

- **`report.ipynb`** — код и результаты выполненных ячеек; его можно повторно исполнить в окружении проекта, пока доступны записанные в нём абсолютные входные пути.
- **`report.html`** — самодостаточный отчёт с таблицами, встроенными графиками и выводами. Для просмотра не требуются CSV, notebook, соседние изображения или подключение к Интернету.

Порядок разделов: входной путь и SHA-256 → размеры и период покупок → проверки → описательная статистика → три графика → итог.

Обязательные проверки: точные колонки и их порядок, типы и разбираемость дат, непустой датасет, отсутствие пропусков, уникальность `(order_id, order_item_id)`, неубывание времени покупки и конечная положительная цена. В ошибке проверки приводятся фактическое значение и ожидаемое условие. Цепочка «оплата ≤ перевозчик ≤ доставка» не требуется. Исполнение прекращается при первой ошибке; пропуски не импутируются, дубликаты не удаляются.

В каждом успешном отчёте **ровно три графика**, все доли — по позициям заказа:

1. Цена: гистограмма с 30 интервалами, логарифмической осью BRL и долей позиций в каждом интервале; весь диапазон без обрезки хвостов.
2. Категории товаров: горизонтальные столбцы top-10 по этому датасету и группы «Прочие»; равные частоты разрешаются по алфавиту.
3. Штаты покупателей: горизонтальные столбцы долей в алфавитном порядке, без дедупликации заказов или покупателей.

EDA описывает один датасет и не принимает решения о дрейфе.

### Создание или перезапись эталона: `init`

```bash
uv run prak init \
  --batch data/olist-stream/batches/batch_000.csv \
  --reference data/olist-stream/reference.csv \
  --output-dir data/olist-stream/reports/step_000
```

Все три пути обязательны. Команда:

1. Строго загружает батч и выполняет обязательные проверки.
2. Создаёт или **перезаписывает** `--reference`, сохраняя схему, CSV-форматы и сортировку по времени покупки и ключу позиции.
3. Вызывает тот же EDA для уже сохранённого эталона; отчёт размещается в `<output-dir>/eda/report.ipynb` и `<output-dir>/eda/report.html`.

Эталон — один физический CSV. Повторный `init` полностью заменяет его выбранным батчем. `manifest.json`, `state.json` и прежние отчёты не нужны. Каталоги создаются автоматически; одноимённые отчёты перезаписываются. Для истории задавайте отдельный `--output-dir` на каждый шаг.

Ошибка проверки батча возникает до записи эталона. Если EDA упал после записи, новый эталон остаётся на диске; отката нет. При ошибке notebook сохраняется доступный частичный вывод, полный HTML не гарантируется.

Коды завершения: `0` — успех, `2` — неверные аргументы CLI, `1` — ошибка данных, исполнения notebook или записи. У `eda` и `init` нет параметров дрейфа. Справка: `uv run prak eda --help`, `uv run prak init --help`.

### Python API и проверка

```python
from prak.auto_eda import report_dataset
from prak.update import initialize_reference

report = report_dataset("data/olist-stream/reference.csv", "data/manual-reports/eda")
print(report.notebook_path, report.html_path)

report = initialize_reference(
    "data/olist-stream/batches/batch_000.csv",
    "data/olist-stream/reference.csv",
    "data/olist-stream/reports/step_000",
)
```

Функции принимают `Path | str`, возвращают `ReportPaths` с абсолютными путями отчётов и передают исключения вызывающему коду. Notebook-зависимости `nbformat`, `nbclient`, `nbconvert`, `ipykernel` объявлены явно. `uv run --frozen pytest` проверяет данные, нормировки графиков, исполнение notebook, встроенные изображения HTML, создание/перезапись эталона, ошибки и CLI из другого рабочего каталога. Все постоянные тесты обходятся без локального Olist.

## DEDA и обновление эталона

### Самостоятельное сравнение: `deda`

```bash
uv run prak deda \
  --reference data/olist-stream/reference.csv \
  --batch data/olist-stream/batches/batch_003.csv \
  --output-dir data/manual-reports/deda
```

Принимает один существующий эталон и один батч, сохраняет `report.ipynb` и самодостаточный `report.html` непосредственно в `--output-dir`. CSV остаются прежними. Все три пути обязательны и могут быть относительными.

В отдельном ядре Python исполняются загрузка обоих CSV, обязательные проверки каждого входа, проверка предполагаемого объединения, метрики и графики. В отчёт входят пути и SHA-256 обоих входов, размеры и периоды, таблицы проверок, метрики с порогами и общий `drift_detected`, три сравнительных графика и итог.

**Повторения ключа `(order_id, order_item_id)` в объединении недопустимы.** Повторный батч, частичное пересечение и внутренние дубликаты вызывают ошибку. Повторные покупки одного товара с различными ключами позиции допустимы.

| Признак | Мера | Дрейф по умолчанию |
| --- | --- | --- |
| `price` | KS D — максимальный разрыв эмпирических CDF | `D >= 0.10` |
| `product_category_name` | TVD — `0.5 × Σ abs(p_batch − p_reference)` | `TVD >= 0.10` |
| `customer_state` | TVD | `TVD >= 0.10` |

TVD учитывает **все** значения обоих входов, включая новые и исчезнувшие; отсутствующим значениям соответствует нулевая доля. Общий флаг — логическое ИЛИ трёх результатов. Семплирования нет; одинаковые входы и настройки дают одинаковые метрики. Это инженерные пороги расстояний, а не p-value или калиброванные уровни значимости.

У `deda` и `update` одинаковые необязательные аргументы:

```text
--price-threshold       0.10
--category-threshold    0.10
--state-threshold       0.10
```

Разрешены только конечные числа в `[0, 1]`; сравнение включает границу. Например, порог `0` отмечает дрейф даже при нулевом расстоянии. Дрейф показывается как непройденная проверка его отсутствия, **не вызывает исключения и не блокирует обновление**.

Ровно три сравнительных графика, все доли — по позициям соответствующего входа:

1. Цена: две наложенные гистограммы с общими 30 интервалами по полному диапазону цен, логарифмической осью BRL и отдельной нормировкой каждого входа. Сплошной синий и пунктирный оранжевый контуры различают эталон и батч.
2. Категории: парные горизонтальные столбцы; top-10 определяется по **текущему эталону**, равенства — по алфавиту. Остальные известные категории — «Прочие», отсутствующие в эталоне — «Новые категории»; группы показываются при наличии.
3. Штаты: парные столбцы по объединению штатов обоих входов, алфавитный порядок.

### Инкрементальное обновление: `update`

После `init` первого батча следующий шаг:

```bash
uv run prak update \
  --batch data/olist-stream/batches/batch_001.csv \
  --reference data/olist-stream/reference.csv \
  --output-dir data/olist-stream/reports/step_001
```

1. Требует существующий эталон; отсутствие файла — ошибка.
2. Строит DEDA **до добавления** батча в `<output-dir>/deda/`.
3. Только после успешного исполнения notebook **и сохранения HTML** объединяет CSV, сортирует по времени покупки и ключу позиции и перезаписывает эталон в исходной схеме и форматах.
4. Строит EDA сохранённого обновлённого эталона в `<output-dir>/eda/`.

```text
reports/step_001/
├── deda/
│   ├── report.ipynb
│   └── report.html
└── eda/
    ├── report.ipynb
    └── report.html
```

Батч и каталог шага выбираются явно. Старые отчёты, `manifest.json` и `state.json` для обновления не нужны. Для сохранения истории задавайте новый каталог шага; одноимённые отчёты перезаписываются.

Ошибка DEDA оставляет эталон прежним. Ошибка заключительного EDA происходит уже после записи обновлённого эталона; отката и автоматического повтора нет. | Генератор историй | Семплирование покупок по вероятностям, зависящим от расстояний до пользовательского якоря |
| Ранжирование | `TruncatedSVD` на матрице user–item |
| Балл товара | Скалярное произведение векторов пользователя и товара |
| Обновление ранжировщика | Пакетное переобучение на накопленных обучающих взаимодействиях |
| Оценка ранжирования | `Recall@K`, `NDCG@K`, бинарная релевантность |
| Простой ориентир | Глобальная популярность товаров по обучающим покупкам |
| Хранение | Локальные файлы: CSV, JSON, сериализованные модели и отчёты |

В системе две заменяемые модели: кластеризации и ранжирования. В baseline метки кластеров не обязаны влиять на ранжирование. Генератор использует выбранное пространство признаков и расстояния; непосредственно метки кластеров в формулу вероятностей пока не входят.

```text
Olist → таблица покупок → фиксированная предобработка
                             ├→ MiniBatchKMeans → силуэт
                             └→ расстояния → генератор историй
                                                ↓
                                      матрица user–item
                                                ↓
                                         TruncatedSVD
                                                ↓
                                         баллы → top-K
```

### Предобработка и поток

Предобработка обучается на стартовой части исходных данных и затем фиксируется. Новые батчи проходят через `transform`, после чего кластеризатор обновляется через `partial_fit`.

Переобучение scaler или encoder между батчами изменило бы систему координат сохранённых центров. Поэтому в пределах одной версии пространства сохраняются порядок признаков, масштабы и размерность кодирования.

Числовые признаки масштабируются отдельно от one-hot-блоков. Для известных категорий при полном one-hot-кодировании квадрат расстояния между одинаковыми значениями равен 0, между разными — 2. Неизвестные категории обрабатываются encoder по указанному правилу; их долю нужно отслеживать.

### Генератор модельного датасета

Для каждого синтетического пользователя:

1. Выбирается случайная строка-якорь из исходного набора.
2. Вычисляются расстояния `d_j` от якоря до строк покупок.
3. Вычисляются вероятности `p_j = exp(-d_j / temperature) / sum_l exp(-d_l / temperature)`.
4. Семплируется заданное количество покупок с возвращением: повторные покупки допустимы.

`temperature > 0` регулирует разнообразие покупок. Меньшее значение сильнее концентрирует покупки около якоря. При семплировании строк частота появления товара в исходном наборе также влияет на его суммарную вероятность выбора.

Якоря и полные распределения вероятностей доступны генератору, но не передаются ранжировщику. Готовые датасеты сохраняются вместе с параметрами и seed.

### Ранжирование

Матрица `R` содержит число обучающих покупок каждой пары `(user_id, product_id)`:

- строки — пользователи;
- столбцы — уникальные товары;
- значения — счётчики покупок;
- хранение — разреженная матрица.

После обучения:

- `P = svd.fit_transform(R)` — векторы пользователей;
- `Q = svd.components_.T` — векторы товаров;
- `score(user, item) = P[user] · Q[item]`.

Балл используется для сортировки и не интерпретируется как вероятность покупки. Выдача содержит уникальные товары. Ранее купленные товары разрешено рекомендовать повторно.

По новой истории пользователя его вектор можно получить через `svd.transform`. Это адаптация профиля при фиксированных векторах товаров. У `TruncatedSVD` нет `partial_fit`: обновление самого разложения выполняется новым `fit`. Инкрементальность проекта обеспечивается кластеризацией.

### Оценка и сравнение

- Истории разделяются по времени на `train`, `validation`, `test`.
- Только доступная обучающая история участвует в обучении и построении профиля.
- `validation` используется для выбора параметров и рабочей версии; `test` — для итоговой оценки.
- Релевантные товары — множество уникальных товаров из отложенных покупок пользователя.
- Силуэт считается по текущим назначениям на фиксированной подвыборке в том же преобразованном пространстве.
- Все ранжировщики внутри одного эксперимента оцениваются на одинаковых пользователях, кандидатах, отложенных покупках и значении `top_k`.

Для сравнения сохраняется матрица **«конфигурация пайплайна × модельный датасет»**. Каждая ячейка — отдельное обучение на `train` соответствующего датасета и оценка на его проверочных частях. Состояние моделей и профилей между ячейками не переносится.

Фиксируются число пользователей, число покупок на пользователя, параметры генерации, конкретные сгенерированные события и разбиения. Сравнение внутри столбца показывает качество на одинаковой задаче. Сравнение только диагональных ячеек смешивает качество моделей и сложность разных синтетических задач. Итоговое среднее считается по одному и тому же набору датасетов.

## Дальнейший консольный интерфейс (план)

Работающие `prepare`, `eda`, `deda`, `init` и `update` описаны выше. Модельные команды будут подключены к тому же entry point `prak`; текущий `update` в дальнейшем дополнится модельными этапами.

```bash
uv run prak inference --file data/inference_candidates.csv
uv run prak summary
```

- **Inference:** вход содержит пары `(user_id, product_id)` с товарами-кандидатами. Выход сохраняет эти строки с дополнительной колонкой `predict`, содержащей балл модели. Top-K формируется сортировкой внутри пользователя.
- **Summary:** сохраняет Markdown- или HTML-отчёт о работе системы и возвращает путь к файлу.

## Граница первой версии

MVP работает локально на Python с файловыми хранилищами. Специализированные MLOps-платформы не используются согласно заданию. Docker и CI/CD относятся ко второму заданию.

Текущий практический результат — подготовка рабочего датасета и батчей, автоматические исполняемые EDA/DEDA-отчёты, создание эталона через `init` и последовательная обработка батчей через `update`. Дальнейшее развитие — модельные этапы и эксперименты с рекомендациями.
