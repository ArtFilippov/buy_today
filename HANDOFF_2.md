## 1. Последние решения пользователя

- **MiniBatchKMeans и новое расстояние пропускаем.** Работаем с временной кластеризацией, TimestampDistance и существующими ранжировщиками. Прежний план признаков сохранён в [README](README.md#minibatchkmeans-отложенный-план).
- **Один выбранный ранжировщик на прогон:** Random или SVD. `run` не сравнивает модели и не выбирает победителя. Inference получает явно указанный каталог модели.
- **Новый прогон с `batch_000`**, отдельный каталог результатов. Прежние эксперименты 000/001 не подхватываются как состояние координатора.
- **При ошибке должно быть выброшено исключение.** Команды передают исходное исключение наружу; автоматического восстановления нет. При ошибке до фиксации батча остаются частичные результаты, индекс не продвигается. Повтор на незавершённом шаге также завершается исключением. Docker строит сводку после фиксации: её ошибка не отменяет уже завершённый батч и явно отмечается в логе.
- Согласованный долгосрочный объём — **MVP + Docker + GitHub Actions**, без специализированных MLOps-платформ.
- **Docker:** только `init`, `update`, `inference` на входе образа. `init` сбрасывает прежний эксперимент, выгружает встроенный Olist, готовит поток и обучает первый батч; `update` берёт один следующий; `inference` требует явный каталог модели. Старые логи сохраняются при сбросе. Есть `--verbose` и отдельный лог каждого вызова.
- **Olist скачивается при сборке**, все девять исходных CSV входят в образ. Пользователь отклонил закрепление версии/ожидаемых контрольных сумм. Сборки и тесты выполнять **из Windows через PowerShell / Windows docker.exe**.

## 4. Контракты, которые важно сохранить

### Координатор и файлы

- Первый шаг: эталон/EDA → кластеризация/оценка → истории → один ранжировщик → validation/test. Далее DEDA выполняется до добавления, EDA — после.
- Модельный этап использует накопленный эталон, генератор — только новый батч и предыдущий снимок, ранжировщик — накопленный train и каталог.
- Конфигурация фиксируется в начале, путь/параметры при продолжении должны совпасть. Индекс продвигается только после всех этапов. Состояние одного файла заменяется атомарно; весь шаг не является транзакцией.
- Манифест шага закрепляет SHA-256 метаданных, включая манифест генератора. Внутренние файлы истории дополнительно проверяет сам генератор. Это предотвращает подхват другого корректного, но чужого снимка.
- Модели и оценки ранжирования используют один поток BLAS/OpenMP. Для t-SNE лимит передаётся окружению отдельного notebook-ядра, а не только процессу координатора.
- `reference.csv` содержит текущее накопление. Для повторного исполнения notebook старого шага потребуется соответствующий исторический CSV; готовый HTML уже содержит результаты своего шага.
- Ошибка после записи эталона не откатывает его. Повторный вызов блокируется контрольной суммой/существующим каталогом шага. Восстановление ручное либо новый прогон.
- `summary` читает завершённые шаги и JSON результатов, проверяет их идентичность; исходные CSV, модели и старые HTML для сборки не требуются. Частичный шаг игнорируется.

### Данные, генерация, модели

- Единица Olist — позиция заказа; ключ `(order_id, order_item_id)`, схема 35 колонок в `schema.py`. `working_dataset.csv` включает будущие строки и хвост и не заменяет эталон.
- Дрейф — информационный результат; нарушения данных/пересечение ключей вызывают исключения. EDA/DEDA исполняются в notebook, по три графика на отчёт. JSON экспортируется из тех же расчётов.
- Число кластеров принадлежит реализации алгоритма. Временной бейзлайн полностью переобучается на эталоне и пересчитывает все метки.
- Расстояние имеет `fit` и `pairwise(X, Y=None)`. TimestampDistance — абсолютная разница времени покупки в секундах.
- Силуэт и t-SNE используют одну квотную выборку до 1000 строк и одну матрицу расстояний. Квота — половина новых/прежних строк с добором.
- Ранжировщик связан с кластеризацией **только через моделируемые данные**. Генератор использует расстояние, а не метки кластеров. Якорь выбирается равномерно по строкам; покупки с возвращением по `exp(-d / temperature)`.
- Каждый батч добавляет новых модельных пользователей. Старые пользователи, события, split и якоря сохраняются точно. Синтетический `user_id` отличается от Olist `customer_unique_id`.
- Разбиение историй идёт по синтетическому `event_index`. Каталог включает все товары поступивших батчей, включая не выбранные в покупки.
- Вход ранжировщика — `RankingData(interactions, catalog)`, взаимодействия ровно `user_id/product_id` с повторами; выдача — `predict(user_id, k)`. Купленные товары разрешены, неизвестный пользователь и K вне каталога — ошибки.
- SVD обучается на счётчиках train-покупок, включает весь каталог, обнуляет факторы товаров без train-событий. Равные score разрешаются по `product_id`; размерность не уменьшается автоматически.
- Recall/NDCG используют уникальные отложенные товары и макроусреднение по пользователям; товары вне train остаются в ground truth. Оценка вызывает только `predict`, не обучает модель и не читает якоря.
- Историческое сравнение Random/SVD было на одинаковых снимках. Новый координатор использует одну модель на прогон; автоматический выбор лучшей пользователь отклонил.

## 5. Готовый Docker-этап

- `Dockerfile`: Python 3.13 slim, uv 0.12.6, frozen lock и не-editable установка. Последняя стадия `runtime` — основной образ; независимая стадия `tests` включает pytest и не скачивает Olist. Собраны теги `prak:local`, `prak-tests:local`.
- `.dockerignore` ограничивает контекст кодом, packaging-файлами и тестами. Данные скачивает stdlib-модуль `src/prak/bundled_data.py`: официальный unversioned Kaggle URL, проверка ZIP/CRC и девяти файлов, каталог `/opt/prak/olist`.
- `src/prak/container_cli.py` — отдельный трёхкомандный интерфейс. `src/prak/progress.py` — стандартное логирование стадий; инструментированы существующие подготовка, координатор, EDA/DEDA/notebook и inference. Важно: логгер обработчика назван явно `prak.container_cli`, чтобы `python -m` не переключал его в `__main__` мимо файлового обработчика.
- Один каталог Windows подключается как `/workspace`. Внутри `dataset`, `data`, `run`, `recommendations`, `logs`. Повторный `init` после предварительных проверок удаляет `data/run/recommendations`, перезаписывает девять исходных CSV; `logs` и посторонние файлы сохраняются. Сброс не транзакционный. Для продолжения сохранять внутренний путь `/workspace`.
- Аргументы обучения/подготовки задаются при `init`; `update` читает сохранённые. При исчерпании потока он только пересобирает сводку. Сводка выполняется после фиксации батча; `batch_committed` и `command_succeeded` — разные события.
- Логи пишутся и при ошибках аргументов; справка файлов не создаёт. `--verbose` показывает стадии до начала работы. Inference сохраняет CSV внутри `recommendations`, по умолчанию с уникальным именем.
